# S1-01 · Comptes et outillage (2 h)
Liste : S1 — Repo, Terraform, ingestion BODACC · Échéance : 2026-11-01 · Étiquettes : vert (sans nom) · [Carte Trello](https://trello.com/c/3KnLDjN1)

## Objectif
Partir d'un poste vierge et finir avec : compte GitHub + repo public `data-platform` (MIT), compte AWS dédié au projet avec user IAM admin + MFA, et la chaîne `uv` / Python 3.12 / Terraform ≥ 1.9 / Docker / Claude Code installée et vérifiée — Pourquoi ça compte dans le projet : chaque brique de la plateforme (buckets S3, EMR, Step Functions, agent Bedrock) sera déployée depuis ce poste vers ce compte, et le repo public est la vitrine de la démo S8.

Règle : tout est traité comme sur une machine vierge. Chaque étape = pourquoi, comment installer, où ça atterrit, comment vérifier. Les commandes de vérification sont lancées par l'utilisateur.

## Prérequis
### Homebrew
`brew` ≈ `apt` pour macOS. Formule = binaire CLI (`brew install gh`), cask = application (`brew install --cask docker`). Les binaires atterrissent dans `/opt/homebrew/bin` (Apple Silicon) ou `/usr/local/bin` (Intel), déjà dans le `PATH` si l'installeur a ajouté `brew shellenv` à `~/.zprofile`.
Doc : https://brew.sh · https://docs.brew.sh/Manpage
Exercice 5 min : `brew doctor` doit dire « Your system is ready to brew ». Sinon appliquer ses recommandations.

### Compte AWS : root, IAM, profil CLI
Un compte AWS = un root (email + mot de passe) + des utilisateurs IAM. Le root ne sert qu'à deux choses : activer son propre MFA, créer le premier user admin. Ensuite tout passe par ce user. Côté CLI, un **profil nommé** (`~/.aws/config` + `~/.aws/credentials`) porte les access keys et la région ; `AWS_PROFILE` ou `--profile` le sélectionne. Comme un context kubectl : un profil par compte, jamais `default` pour un projet.
Doc : https://docs.aws.amazon.com/IAM/latest/UserGuide/root-user-best-practices.html · https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-files.html
Exercice 5 min : lire « Root user best practices » et noter en 2 lignes ce que le root peut faire qu'un user IAM `AdministratorAccess` ne peut pas (fermeture du compte, changement de plan de support, certaines actions S3 Object Lock…).

### Python géré par `uv`
`uv` ≈ `pnpm` + `nvm` + `pipx` en un binaire : installe des versions de Python, crée le venv, résout le lockfile. `pyproject.toml` ≈ `package.json`, `uv.lock` ≈ `pnpm-lock.yaml`, `.python-version` ≈ `.nvmrc`, `.venv/` ≈ `node_modules/`. Le Python système (macOS ou Homebrew) ne sert jamais aux projets.
Doc : https://docs.astral.sh/uv/concepts/python-versions/
Exercice 5 min : après l'étape 5, `uv python list` : distinguer les Python « system » des « managed » (chemin sous `~/.local/share/uv/python/`).

### Dépôt public et licence MIT
Repo public = aucun secret, aucun ARN, aucun hostname interne, jamais. `.gitignore` Python + Terraform dès le premier commit : `.venv/`, `__pycache__/`, `.terraform/`, `*.tfstate*`, `*.tfvars`, `.env*`, `.envrc`. Licence MIT = fichier `LICENSE`, année + nom du titulaire.
Doc : https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-new-repository · https://choosealicense.com/licenses/mit/
Exercice 5 min : `curl -s https://raw.githubusercontent.com/github/gitignore/main/Terraform.gitignore` : expliquer en une ligne pourquoi `*.tfvars` est ignoré mais pas `*.tf`.

## Étapes

### [x] Étape 1 — Compte GitHub, `git`, `gh`
- Pourquoi : la carte veut un repo public poussé. `git` commit et pousse ; `gh` (CLI officielle GitHub, ≈ `glab`) crée le repo et règle l'auth depuis le terminal. `gh` n'est pas obligatoire (UI + token PAT marchent) mais il règle l'auth une fois pour toutes et sert dès S3 (PR, issues, secrets Actions) et S4 (l'agent ouvrira des PR).
- À faire :
  1. Compte GitHub perso (https://github.com/signup), jamais un compte client. 2FA : Settings → Password and authentication → app TOTP. Email privé : Settings → Emails → « Keep my email addresses private » → noter l'alias `<id>+<user>@users.noreply.github.com`.
  2. `git` est livré avec macOS (Xcode Command Line Tools). Si `git --version` échoue : `xcode-select --install`.
  3. `brew install gh` puis `gh --version`.
  4. `gh auth login` → GitHub.com → HTTPS → « Authenticate Git with your GitHub credentials? » **Yes** (gh devient credential helper de git) → Login with a web browser → code 8 caractères. Token OAuth stocké dans le keychain, scopes `repo`, `read:org`, `gist`, `workflow`.
  5. Identité globale (`~/.gitconfig`) : `git config --global user.name "…"`, `git config --global user.email "<alias noreply>"`, `git config --global init.defaultBranch main`. Un repo client surcharge avec `git config user.email …` sans `--global`.
- Indice : si `git push` demande un mot de passe plus tard, un ancien helper `osxkeychain` passe avant `gh`. `git config --global --get-all credential.helper` doit contenir `gh auth git-credential`.
- Vérifier : `gh auth status` → « Logged in to github.com account … » ; `git config --global --get user.email` → alias noreply.

### [ ] Étape 2 — Créer le compte AWS dédié
- Pourquoi : la carte impose un compte dédié, jamais celui d'un client. Un compte = frontière de facturation (garde-fous S1-02) et de sécurité (rien du projet ne peut toucher un compte SACEM).
- À faire :
  1. https://portal.aws.amazon.com/billing/signup avec un email dédié (alias `+aws-data-platform` suffit), carte bancaire, plan de support Basic (gratuit).
  2. Se connecter en root une seule fois. Activer MFA : coin supérieur droit → Security credentials → « Assign MFA device » → app TOTP.
  3. Noter l'ID de compte (12 chiffres) dans ton gestionnaire de secrets, pas dans un fichier du repo.
  4. Ne rien créer d'autre avec le root. Se déconnecter.
- Indice : l'ID de compte est dans le menu en haut à droite. Il n'est pas secret au sens strict mais ne doit pas apparaître dans un repo public (il facilite le ciblage).
- Vérifier : reconnexion root → MFA demandé. Console IAM → Dashboard → « Security recommendations » : « Root user has MFA » coché.

### [ ] Étape 3 — Utilisateur IAM admin + MFA + access keys
- Pourquoi : le quotidien se fait avec un user IAM révocable, jamais avec le root. Les access keys sont l'identité programmatique de la CLI et de Terraform (≈ un token de CI).
- À faire :
  1. Console IAM → Users → Create user `fraoucene-data`, cocher « Provide user access to the AWS Management Console », mot de passe à changer à la première connexion.
  2. Permissions → « Attach policies directly » → `AdministratorAccess` (policy managée AWS ; on restreindra plus tard si besoin).
  3. Se déconnecter du root, se connecter en `fraoucene-data`, activer MFA sur ce user (Security credentials → Assign MFA device).
  4. Security credentials → Access keys → Create → use case « Command Line Interface » → télécharger le CSV une seule fois, le stocker dans le gestionnaire de secrets, supprimer le CSV.
- Indice : une seule paire de keys active par usage. Si elle fuit, on la désactive ici, sans toucher au root.
- Vérifier : en `fraoucene-data`, IAM → Users → `fraoucene-data` → Security credentials : 1 MFA device assigné, 1 access key « Active ».

### [ ] Étape 4 — AWS CLI v2 et profil `data-platform`
- Pourquoi : la CLI est l'outil de vérification de toute la suite (`aws s3 ls`, `aws sts …`) et Terraform réutilise ses profils.
- À faire :
  1. `brew install awscli` (ou le pkg officiel https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html). `aws --version` doit afficher `aws-cli/2.x`.
  2. `aws configure --profile data-platform` : access key, secret key (étape 3), région `eu-west-3` (Paris) ou `eu-west-1` (Irlande, plus de services), sortie `json`. Écrit dans `~/.aws/credentials` et `~/.aws/config`.
  3. Sélection du profil : `export AWS_PROFILE=data-platform` dans le shell, ou un `.envrc` avec `direnv` (`brew install direnv`), **jamais versionné**.
- Indice : précédence des credentials : variables d'env > profil `AWS_PROFILE` > `default`. Si `aws sts get-caller-identity` renvoie un autre compte, une variable `AWS_ACCESS_KEY_ID` traîne dans l'env.
- Vérifier : `aws sts get-caller-identity --profile data-platform --query '[Account,Arn]' --output text` → ID du compte de l'étape 2 et `arn:aws:iam::…:user/fraoucene-data`.

### [ ] Étape 5 — Installer `uv`
- Pourquoi : un seul outil pour les versions de Python, les venv, les dépendances et le lockfile. Remplace `pyenv` + `pip` + `venv` + `poetry`.
- À faire : installeur officiel `curl -LsSf https://astral.sh/uv/install.sh | sh` (binaire dans `~/.local/bin/`, ajoute le `PATH` à `~/.zshrc` si besoin) ou `brew install uv`. Relancer le shell.
- Indice : l'installeur officiel permet `uv self update` ; via Homebrew c'est `brew upgrade uv`. Ne pas mélanger les deux.
- Vérifier : `uv --version` renvoie une version et `command -v uv` un chemin.

### [ ] Étape 6 — Python 3.12 géré par `uv`
- Pourquoi : la carte impose 3.12. Les lambdas RLINK sont en 3.12, Spark EMR 7.x aussi : même version partout évite les surprises de syntaxe.
- À faire :
  1. `uv python install 3.12` : télécharge un build standalone sous `~/.local/share/uv/python/`.
  2. Dans le clone `data-platform/` : `uv python pin 3.12` écrit `.python-version` (≈ `.nvmrc`), à versionner.
  3. Ne pas créer de venv à la main : `uv run` le fait à la demande.
- Indice : `uv python find 3.12` montre quel binaire sera utilisé. Si c'est `/usr/bin/python3` ou un Homebrew, le pin n'est pas pris.
- Vérifier : `uv run python -c "import sys; print(sys.version.split()[0], sys.executable)"` → `3.12.x` et un chemin sous `~/.local/share/uv/python/`.

### [x] Étape 7 — Terraform ≥ 1.9
- Pourquoi : l'IaC de S1-04 et de tout le projet. ≥ 1.9 pour `removed`, `import` par bloc, validations de variables croisées.
- À faire : tap officiel HashiCorp : `brew tap hashicorp/tap && brew install hashicorp/tap/terraform`. Alternative multi-versions (≈ `nvm`) : `brew install tfenv && tfenv install latest && tfenv use latest`.
- Indice : plus tard, `required_version = ">= 1.9"` dans `terraform {}` verrouille côté code. Pour OpenTofu, `brew install opentofu` ; même syntaxe, mais choisis un seul outil.
- Vérifier : `terraform version -json | python3 -c "import json,sys; v=json.load(sys.stdin)['terraform_version']; print(v); assert tuple(map(int,v.split('.')))>=(1,9)"`.

### [ ] Étape 8 — Docker
- Pourquoi : images de job Spark en local (S2), tests d'intégration avec Postgres/LocalStack (S3), build des lambdas conteneurisées.
- À faire : `brew install --cask docker` (Docker Desktop) puis ouvrir l'app une fois pour lancer le démon. Alternatives légères : OrbStack (`brew install --cask orbstack`) ou Colima (`brew install colima docker && colima start`).
- Indice : sans démon lancé, `docker info` échoue sur « Cannot connect to the Docker daemon at unix:///var/run/docker.sock ». Ce n'est pas un problème d'installation.
- Vérifier : `docker info --format '{{.ServerVersion}}'` renvoie une version et `docker run --rm hello-world` affiche « Hello from Docker! ».

### [ ] Étape 9 — Claude Code
- Pourquoi : assistant principal de dev du projet et, en S4+, base de l'agent. Un `CLAUDE.md` dans le repo lui donne le contexte à chaque session.
- À faire :
  1. Installer selon https://docs.claude.com/en/docs/claude-code/setup (installeur natif ou `npm install -g @anthropic-ai/claude-code`). Se connecter au premier lancement.
  2. Dans `data-platform/`, créer `CLAUDE.md` (10 lignes) : stack (Python 3.12 via `uv`, Terraform, AWS eu-west-3), « toujours `uv run` », « jamais de secret ni d'ID de compte dans le repo », format de commit (`main: message`).
- Indice : `claude --version` suffit pour la carte. Les skills et plugins viendront en S4.
- Vérifier : `claude --version` renvoie une version ; `test -f CLAUDE.md && echo ok`.

### [ ] Étape 10 — Repo `data-platform` : `.gitignore`, commit, push, vérif public
- Pourquoi : critère d'acceptation de la carte. État au 2026-10-20 : repo `github.com/fraoucene/data-platform` créé depuis l'UI GitHub (commit « Initial commit » : LICENSE MIT + README une ligne), cloné dans `~/Desktop/workspace/data-platform`, branche `main`, visibilité `public`. Il manque le `.gitignore`, à pousser avant tout code.
- Concept : un fichier déjà commité reste dans l'historique même après ajout au `.gitignore`. D'où le `.gitignore` avant le premier fichier généré (`.venv/`, `.terraform/`).
- À faire, dans `data-platform/` :
  1. `.gitignore` : concaténer les gitignore officiels GitHub `Python.gitignore` et `Terraform.gitignore`, ajouter `.env*`, `.envrc`, `.DS_Store`. `*.tfvars` reste ignoré, `!*.auto.tfvars.example` autorisé.
  2. Tester les patterns sans créer les fichiers : `git check-ignore -q .venv .terraform terraform.tfstate .env .envrc && echo ignoré`.
  3. Commit avec le préfixe de branche : `git add .gitignore && git commit -m "main: add Python + Terraform gitignore"`.
  4. `git push`. Avec `gh` configuré à l'étape 1, pas de mot de passe demandé.
- Indice : `learning/` est versionné volontairement (journal d'apprentissage, aucun secret dedans). Pour le garder hors du repo public, l'ajouter au `.gitignore` maintenant, avant le premier push qui le contient.
- Vérifier : `git log --oneline | wc -l` → 2 ; `curl -s https://api.github.com/repos/fraoucene/data-platform | python3 -c "import json,sys; d=json.load(sys.stdin); print(d['visibility'], d['license']['spdx_id'])"` → `public MIT`.

## Pièges courants (dev TS → Python)
1. `pip install` nu ≈ `npm install -g` pour tout. En Python il n'y a pas de `node_modules` implicite : tout passe par `uv add` / `uv run`, jamais `pip` direct.
2. `.venv/` ≈ `node_modules/` : jamais versionné, régénéré par `uv sync` depuis `uv.lock`. Un `.venv/` poussé par erreur pèse des centaines de Mo.
3. Credentials AWS : pas de `dotenv` chargé automatiquement comme en Node. La CLI et boto3 lisent `AWS_PROFILE` / `~/.aws/*`. Un `.env` poussé dans un repo public est repéré par des scanners en quelques minutes.
