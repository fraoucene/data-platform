# S1-04 · Terraform de base (4 h)
Liste : S1 — Repo, Terraform, ingestion BODACC · Échéance : 2026-11-01 · Étiquettes : orange · [Carte Trello](https://trello.com/c/Pq2D6W9L)

## Objectif
Passer `infra/` d'un état local à un vrai socle : backend S3 verrouillé, modules `kms`, `s3-buckets` (raw, processed, out, artifacts, logs) et `iam` (rôles Lambda, EMR, Step Functions), pilotés par `make up` / `make down` — Pourquoi ça compte dans le projet : chaque brique suivante (ingestion BODACC, jobs Spark, Step Functions, agent) écrit dans ces buckets avec ces rôles ; si le socle est flou, chaque carte rouvre les questions de chiffrement, de droits et de nommage.

## Prérequis
### Backend S3 et verrou d'état
Le backend `s3` stocke `terraform.tfstate` dans un bucket (`key` = chemin de l'objet) et pose un verrou pendant `plan`/`apply` pour éviter deux applies concurrents. Deux mécanismes de verrou : table DynamoDB (`dynamodb_table`, historique, déprécié depuis Terraform 1.11 mais fonctionnel) ou verrou natif S3 (`use_lockfile = true`, Terraform ≥ 1.10, objet `.tflock` à côté de l'état, aucune ressource en plus). Le bloc `backend` n'accepte ni variable ni expression : configuration partielle via `-backend-config=backend.hcl`. Passer d'un état local à S3 se fait avec `terraform init -migrate-state`, qui copie l'état existant sans recréer les ressources.
Doc : https://developer.hashicorp.com/terraform/language/backend/s3 · https://developer.hashicorp.com/terraform/language/backend#partial-configuration
Exercice 5 min : lire la section « State Locking » de la doc backend s3. Noter ce qu'il faut comme permissions IAM minimales pour le bucket d'état avec `use_lockfile` (3 actions S3) et ce que DynamoDB ajouterait.

### Bootstrap : qui crée le bucket d'état ?
Le bucket d'état ne peut pas être géré par l'état qu'il stocke (il faudrait qu'il existe avant son propre `apply`). Pattern standard : un mini-root `infra/bootstrap/` à état local qui ne gère que le bucket d'état (+ la table de verrou), appliqué une fois, quasi jamais modifié. Le root principal `infra/` consomme ce bucket via son backend. Si l'état local du bootstrap est perdu, les deux ressources se réimportent en deux commandes `terraform import`.
Doc : https://developer.hashicorp.com/terraform/cli/commands/import · https://developer.hashicorp.com/terraform/language/state/remote
Exercice 5 min : écrire sur papier l'ordre exact des commandes pour une machine vierge qui doit reconstruire `dev` (bootstrap → backend → up). Combien d'`init` ? Lesquels ont besoin de `-migrate-state` ? Aucun, pourquoi ?

### Ressources S3 éclatées et `for_each`
Depuis le provider AWS 4, `aws_s3_bucket` ne porte plus que le nom : versioning, chiffrement, lifecycle, logging, public access block sont des ressources séparées, chacune avec `bucket = aws_s3_bucket.x.id`. Cinq buckets identiques = `for_each = toset(var.names)` sur chaque ressource, `each.key` dans le nom, et des outputs en map (`{ for k, b in aws_s3_bucket.this : k => b.arn }`). Les noms S3 sont globaux : suffixer par l'account id (`data.aws_caller_identity`), jamais écrit en dur.
Doc : https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/s3_bucket · https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/s3_bucket_lifecycle_configuration
Exercice 5 min : dans la doc `aws_s3_bucket_lifecycle_configuration`, trouver pourquoi la doc recommande un bloc `filter {}` explicite dans chaque règle (alors que le provider 6.69 l'accepte absent) et ce que fait `noncurrent_version_expiration` sur un bucket versionné.

### KMS : clé, alias, politique, rotation
Une clé KMS (`aws_kms_key`) a une politique propre (qui peut l'utiliser), une rotation annuelle optionnelle (`enable_key_rotation`) et une fenêtre de suppression de 7 à 30 jours (jamais immédiate). L'alias (`aws_kms_alias`, `alias/…`) est le nom stable : les consommateurs référencent l'ARN de la clé, les humains l'alias. Chiffrer S3 avec `aws:kms` + `bucket_key_enabled = true` divise les appels KMS (et leur coût) par bucket au lieu de par objet.
Doc : https://docs.aws.amazon.com/kms/latest/developerguide/key-policies.html · https://docs.aws.amazon.com/AmazonS3/latest/userguide/bucket-key.html
Exercice 5 min : lire « Default key policy ». Pourquoi une clé créée par Terraform sans `policy` reste utilisable par les rôles IAM du compte ? Quel est le risque si on écrit une `policy` custom sans la clause root ?

### IAM : trust policy vs permissions, `aws_iam_policy_document`
Un rôle = une trust policy (qui peut l'assumer : `lambda.amazonaws.com`, `elasticmapreduce.amazonaws.com`, `states.amazonaws.com`) + des permissions (managed ou inline). `data "aws_iam_policy_document"` construit le JSON avec validation à `plan` (≈ builder typé plutôt que `jsonencode` d'une map libre). Moindre privilège S3 : deux ARN par bucket (`arn` pour `ListBucket`, `arn/*` pour `GetObject`/`PutObject`). KMS : `Decrypt`/`Encrypt`/`GenerateDataKey` sur l'ARN de la clé.
Doc : https://registry.terraform.io/providers/hashicorp/aws/latest/docs/data-sources/iam_policy_document · https://docs.aws.amazon.com/emr/latest/ManagementGuide/emr-iam-roles.html
Exercice 5 min : dans la doc EMR, distinguer le service role et l'instance profile (EC2). Lequel la carte demande-t-elle ? Qu'est-ce qui manquerait pour lancer un vrai cluster ?

### default_tags et ressources non taggables
`default_tags` du provider s'applique aux ressources des modules enfants (le provider est hérité). Mais beaucoup de ressources n'ont pas d'attribut `tags` : `aws_s3_bucket_versioning`, `aws_kms_alias`, `aws_iam_role_policy`, `aws_s3_bucket_public_access_block`… « Aucune ressource sans tag » = aucune ressource **taggable** sans tag ; l'audit (`infra/scripts/check_tags.py` de S1-02) ignore déjà celles sans `tags_all`. Les tags d'environnement (`environment = dev`) se fusionnent avec `merge()`.
Doc : https://registry.terraform.io/providers/hashicorp/aws/latest/docs/guides/resource-tagging
Exercice 5 min : dans la doc du provider, lister pour `aws_kms_key`, `aws_iam_role`, `aws_s3_bucket`, `aws_dynamodb_table` lesquels ont `tags` et vérifier que `aws_s3_bucket_lifecycle_configuration` n'en a pas.

## Étapes
### [x] Étape 1 — Bootstrap du backend : bucket d'état et verrou
- À faire : un second root Terraform `infra/bootstrap/`, indépendant, à état local, qui ne gère que le bucket d'état de `infra/`. Décision : verrou `use_lockfile = true`, pas de DynamoDB → 4 ressources.
  1. `versions.tf` : `required_version >= 1.10` (minimum pour `use_lockfile`), provider `hashicorp/aws ~> 6.0`. ≈ `package.json` : engines + deps.
  2. `providers.tf` : région, profil, `default_tags`. ≈ config du SDK. `variables.tf` : `region` défaut `eu-west-3` (décision projet, versionnée), `profile` défaut `null` (local à la machine, dans le tfvars gitignoré), `tags` défaut `project`, `component = tfstate`, `managed_by`. Pas d'`environment` : le bucket est unique pour le compte et stockera `dev/` et `prod/`.
  3. `main.tf` : `data "aws_caller_identity"` (lecture AWS sans créer, ≈ GET) → `locals` `state_bucket = "data-platform-tfstate-${account_id}"`. Provider 6 : un bucket = 4 ressources reliées par `bucket = aws_s3_bucket.tfstate.id` : `aws_s3_bucket` (`prevent_destroy = true`), `aws_s3_bucket_versioning` Enabled, SSE `AES256`, `aws_s3_bucket_public_access_block` 4 × `true`.
  4. `outputs.tf` : `state_bucket`, `region`, à reporter dans `infra/backend.hcl` (étape 2). `README.md` : pourquoi un root séparé, verrou, commandes, les 4 `terraform import` de secours.
  5. Profil : plusieurs profils dans `~/.aws/config` → toujours expliciter. `profile = "data-platform"` dans `infra/bootstrap/local.auto.tfvars` **et** `infra/local.auto.tfvars` (gitignorés). Vérif compte : `aws sts get-caller-identity --profile data-platform --query Account --output text`.
  6. `terraform -chdir=infra/bootstrap init` (télécharge le provider dans `.terraform/`), `plan` (lire : 4 `+ resource`, `(known after apply)` sur arn/id), `apply` → `yes`.
- Concept : œuf et poule : le bucket d'état vit dans un état séparé, local, minuscule. Terraform 1.14 : `dynamodb_table` fonctionne mais est déprécié (avertissement à chaque `init`) ; `use_lockfile = true` le remplace sans table. Décision à prendre et à noter dans le journal : la carte dit DynamoDB, le provider dit lockfile.
- Question : pourquoi un dossier `bootstrap` séparé, c'est de la réutilisation ? → non, un second projet Terraform avec son propre état. Terraform doit écrire son état quelque part : pour l'écrire dans S3, le bucket doit exister avant. Œuf et poule → mini-root à état local. Le nom `bootstrap` est une convention (aussi `seed/`, `tf-backend/`).
- Question : les tags servent à quoi ? → coût (facture filtrable par `project`, le budget S1-02 est branché dessus), inventaire (`environment = dev` = périmètre de `make down`), traçabilité (`managed_by = terraform` = pas de modif console). `default_tags` les pose partout, `check_tags.py` vérifie.
- Question : pourquoi AES256 ici et `aws:kms` partout ailleurs ? → la clé KMS sera créée par l'état que ce bucket stocke : elle ne peut exister qu'après lui. Dépendance circulaire. AES256 est géré par S3 sans ressource : il coupe la boucle.
- Question : `apply` sans `plan` ? → `apply` inclut le plan et s'arrête sur `Enter a value:` avant de créer. `plan` séparé = relire sans pouvoir dire oui, ou `-out=tfplan` pour appliquer plus tard à l'identique (CI, `make plan`).
- Erreur vue : consigne « copier `local.auto.tfvars.example` » donnée puis retirée → incohérence du tuteur, qui avait supposé un profil nommé sans vérifier. Leçon retenue : `grep '^\[' ~/.aws/config` d'abord ; plusieurs profils → profil explicite partout, jamais le défaut.
- Indice : si tu choisis `use_lockfile`, la table DynamoDB disparaît du bootstrap et le critère « lock » se vérifie avec un objet `dev/terraform.tfstate.tflock` pendant un `apply`. Dans les deux cas, l'état local du bootstrap (`infra/bootstrap/terraform.tfstate`) est ignoré par git : documenter les deux `terraform import` de secours dans `infra/bootstrap/README.md`.
- Vérifier : `terraform -chdir=infra/bootstrap apply` → `Apply complete! Resources: 5 added` (4 si lockfile) ; `aws s3api get-bucket-versioning --bucket $(terraform -chdir=infra/bootstrap output -raw state_bucket) --query Status --output text` → `Enabled` ; `aws dynamodb describe-table --table-name data-platform-tf-lock --query Table.TableStatus --output text` → `ACTIVE`
- Résultat : `Apply complete! Resources: 4 added`, outputs `region = eu-west-3` et `state_bucket = data-platform-tfstate-<account_id>`. Pas de DynamoDB (lockfile). `terraform fmt -check` OK, `terraform.tfstate` et `local.auto.tfvars` du bootstrap ignorés par git. Fichiers écrits par le tuteur, relus.

### [x] Étape 2 — Backend S3 et migration de l'état existant
- À faire : migrer l'état local de `infra/` vers S3, et structurer la config multi-env dès maintenant (un code, un dossier de config par env).
  1. `infra/backend.tf` : bloc `backend "s3"` réduit à `encrypt = true`. Le bloc backend n'accepte aucune variable : tout ce qui dépend du compte ou de l'env vient d'un `.hcl` passé à `init -backend-config=`. `.hcl` et pas `.tf` : Terraform charge tous les `*.tf` automatiquement, un `.hcl` seulement sur demande.
  2. Garde-fou compte : `allowed_account_ids = [var.account_id]` dans les deux `providers.tf`, variable `account_id` validée sur 12 chiffres. Si le profil pointe sur un autre compte, Terraform refuse avant de toucher quoi que ce soit.
  3. Structure `infra/envs/dev/` : `dev.tfvars` commité (`environment`, `budget_limit_usd`), `backend.hcl` gitignoré (`bucket`, `key = "dev/terraform.tfstate"`, `region`, `profile`, `use_lockfile = true`) + `.example`, `local.tfvars` gitignoré (`profile`, `account_id`, `alert_email`) + `.example`. `.gitignore` : `!infra/envs/*/*.tfvars` puis `infra/envs/*/local.tfvars` (la dernière règle qui matche gagne). `infra/local.auto.tfvars` déplacé dans `envs/dev/local.tfvars`.
  4. `Makefile` : `ENV ?= dev`, `TF_VARS = -var-file=envs/$(ENV)/$(ENV).tfvars -var-file=envs/$(ENV)/local.tfvars`, cibles `tf-init` (`-backend-config=envs/$(ENV)/backend.hcl -input=false -reconfigure`), `tf-fmt`, `tf-validate`, `plan` (`-out=tfplan` puis `check_tags.py`), `up`, `down`. Préfixe `tf-` = plomberie, `plan`/`up`/`down` = usage quotidien.
  5. Migration : `terraform -chdir=infra init -backend-config=backend.hcl -migrate-state` → `yes` à « copy existing state ». Terraform supprime lui-même l'état local après la copie. Puis `make plan` → `No changes`.
- Concept : configuration partielle du backend : le bloc ne peut pas lire `var.*`, donc tout ce qui dépend du compte passe par `-backend-config`. `-migrate-state` copie l'état local vers S3 sans toucher aux ressources : un `plan` juste après doit être vide. L'état contient des valeurs sensibles potentielles (outputs, attributs) : chiffrement côté S3 + bucket privé, jamais dans git.
- Question : `infra/terraform.tfstate` local après migration, danger ? → Terraform l'ignore (backend actif enregistré dans `.terraform/terraform.tfstate`, à garder), mais il contient l'état complet en clair et sème la confusion : `trash`. Ici `-migrate-state` l'avait déjà retiré.
- Question : comment gérer dev / int / prod et la CI ? → un seul code, `envs/<env>/` par env, un état par env (`key`), idéalement un compte AWS par env (un bootstrap par compte). Poste de dev = dev seul (pas de `envs/prod/local.tfvars` local). CI GitLab : `backend.hcl` généré depuis les variables CI, secrets par `TF_VAR_<nom>` scopés par environment, credentials AWS par OIDC (rôle par env, pas de clé), `plan` en MR avec `tfplan` en artefact, `apply dev` auto sur `main`, `apply int`/`prod` manuels sur environments protégés, `apply` rejoue exactement le `tfplan` du job précédent.
- Question : pourquoi `tf-init` préfixé et pas `plan` ? → `tf-` = cible interne Terraform, pour ne pas confondre avec le monde Python du même Makefile. `plan`/`up`/`down` = commandes du quotidien, elles appellent `tf-init` toutes seules.
- Erreur vue : `trash infra/terraform.tfstate` → `doesn't exist` : `init -migrate-state` supprime l'état local après copie. Rien à faire.
- Erreur vue : `echo 'profile = …' >> infra/local.auto.tfvars` sans retour à la ligne final → `Missing newline after argument`, `budget_limit_usd = 35profile = …`. Toujours relire un fichier après un `>>`, ou utiliser `printf '\n…'`.
- Indice : si `init` propose `-reconfigure` au lieu de migrer, c'est qu'un `.terraform/terraform.tfstate` (métadonnées backend) traîne : lis le message, ne force pas avant d'avoir compris. `terraform state pull | head -5` montre `"serial"` et `"lineage"` : la lineage doit être la même avant/après migration.
- Vérifier : `terraform -chdir=infra init -backend-config=backend.hcl -migrate-state` → `Successfully configured the backend "s3"` ; `terraform -chdir=infra state list` → `aws_budgets_budget.monthly_cost`, `aws_sns_topic.budget_alerts`, … ; `aws s3 ls s3://$(terraform -chdir=infra/bootstrap output -raw state_bucket)/dev/` → `terraform.tfstate` ; `terraform -chdir=infra plan -var-file=local.auto.tfvars` → `No changes.`
- Résultat : `Successfully configured the backend "s3"`, `state list` → 6 entrées (budget, topic, policy, subscription, 2 data), `dev/terraform.tfstate` dans le bucket (12,9 Ko), `make plan` → `No changes`, `check_tags.py` silencieux = 0 violation. Structure `envs/dev/` + Makefile `ENV=` en place. Fichiers écrits par le tuteur, déplacements faits par Fraoucene.

### [x] Étape 3 — Module `kms`
- À faire : contexte. KMS = coffre à clés de chiffrement du compte : tu ne vois jamais la clé, tu demandes à AWS de chiffrer/déchiffrer, chaque demande est une opération IAM autorisable et journalisée (CloudTrail). Trois objets : la clé (ARN opaque, rotation annuelle, suppression différée 7 à 30 j), l'alias (nom lisible `alias/…`, stable), la politique de clé (par défaut déléguée à IAM). Pourquoi ici : une seule clé pour tous les buckets = seconde serrure indépendante de la policy S3 (sans `kms:Decrypt`, `s3:GetObject` ne suffit pas), audit de qui déchiffre, révocation globale en un geste. Objectif : clé `Enabled` + rotation `True` + alias `alias/data-platform-dev`, via un module réutilisable, ARN exposé pour les étapes 4 et 6.
  1. `infra/modules/kms/` : `versions.tf` (`required_providers` seul, pas de `required_version` dans un module), `variables.tf` (`name` obligatoire, `description`, `deletion_window_in_days` défaut 7 validé 7 à 30), `main.tf` (`aws_kms_key.this` avec `enable_key_rotation = true`, `aws_kms_alias.this` `alias/${var.name}` → `target_key_id`), `outputs.tf` (`key_arn`, `key_id`, `alias_name`).
  2. `infra/main.tf` (nouveau) : `locals.prefix = "data-platform-${var.environment}"`, repris par tous les modules ; `module "kms" { source = "./modules/kms" name = local.prefix }`.
  3. `infra/outputs.tf` : `kms_key_arn = module.kms.key_arn`, `kms_alias = module.kms.alias_name`. Depuis le root on ne lit d'un module que ses `output` : interface publique, le reste est privé.
  4. `make plan` (init prend le nouveau module) → `Plan: 2 to add`, adresses `module.kms.*` ; `make up`.
- Concept : un module Terraform ≈ un composant : `variables.tf` = props, `outputs.tf` = valeurs retournées, provider et `default_tags` hérités du root sans rien déclarer (sauf `required_providers` dans `versions.tf` du module, bonne pratique). Pas de `policy` custom sur la clé à ce stade : la politique par défaut délègue aux policies IAM du compte, ce qui suffit pour des rôles du même compte.
- Question : `deletion_window_in_days = 7`, que se passe-t-il entre `make down` et `make up` enchaînés ? → alias supprimé immédiatement ; clé en `PendingDeletion` 7 j (récupérable par `cancel-key-deletion`, inutilisable pour chiffrer). `make up` crée une nouvelle clé (nouvel ARN) et recrée l'alias. Objets chiffrés avec l'ancienne illisibles après 7 j (buckets vides au `down`, donc rien de perdu). `AlreadyExistsException` possible si l'alias n'est pas encore libéré : attendre.
- Question : le chiffrement KMS, concrètement ça change quoi ? → rien au quotidien (S3 chiffre/déchiffre à la volée). Visible dans 4 cas : rôle avec `s3:GetObject` sans `kms:Decrypt` → `AccessDenied` (seconde serrure) ; audit CloudTrail de chaque `Decrypt` ; révocation globale en désactivant la clé, même pour des copies déjà faites ; conformité « clé gérée par le client ». Coût 1 $/mois/clé + appels, réduits par `bucket_key_enabled`. AES256 protège contre le vol de disque chez AWS, KMS contre un mauvais droit IAM ou un bucket mal configuré.
- Question : pourquoi `resource "aws_kms_key" "this"` ? → nom local (jamais visible dans AWS), convention des modules à ressource unique : l'adresse `module.kms.aws_kms_key.this` évite la redondance. Dans un root on nomme par rôle (`aws_sns_topic.budget_alerts`).
- Question : `module.kms.alias_name` est défini où ? → `output "alias_name"` dans `modules/kms/outputs.tf`, qui expose `aws_kms_alias.this.name`. Chaîne : ressource → `output` du module → `module.kms.<output>` dans le root → `output` du root. Deux noms (`alias_name` dedans, `kms_alias` dehors) : le module est générique, le root préfixe pour lever l'ambiguïté.
- Indice : `deletion_window_in_days = 7` est le minimum : `make down` planifie la suppression, il ne détruit pas la clé tout de suite, mais l'alias est libéré immédiatement et `make up` peut recréer une clé avec le même alias. Chaque module a son propre `versions.tf` avec `required_providers` (sans `required_version`).
- Vérifier : `terraform -chdir=infra apply -var-file=local.auto.tfvars` → `Resources: 2 added` ; `aws kms describe-key --key-id alias/data-platform-dev --query KeyMetadata.KeyState --output text` → `Enabled` ; `aws kms get-key-rotation-status --key-id "$(terraform -chdir=infra output -raw kms_key_arn)" --query KeyRotationEnabled --output text` → `True` (cette commande, comme `get-key-policy`, refuse un alias : `InvalidArnException` ; il faut l'id ou l'ARN de la clé, alors que `describe-key` accepte l'alias)
- Résultat : `Apply complete! Resources: 2 added`, outputs `kms_alias = alias/data-platform-dev` et `kms_key_arn = arn:aws:kms:eu-west-3:<account_id>:key/<uuid>`. `terraform validate` OK avant apply. Module écrit par le tuteur, relu ; `make plan`/`make up` lancés par Fraoucene.

### [x] Étape 4 — Module `s3-buckets` : cinq buckets chiffrés et versionnés
- À faire : contexte. S3 = stockage d'objets : fichiers dans des buckets, adressés par une clé qui ressemble à un chemin, pas de dossiers réels. Nom de bucket unique au monde → suffixe account id. Provider 6 : un bucket = 4 ressources séparées (bucket, blocage public, versioning, chiffrement). Pourquoi cinq : architecture medallion, chaque bucket a un rôle et des droits différents (`raw` écrit par la Lambda d'ingestion, lu par les jobs ; `processed` Parquet nettoyé ; `out` exports ; `artifacts` zips/jars ; `logs` logs d'accès). Séparer = moindre privilège lisible à l'étape 6. Objectif : 5 buckets `data-platform-dev-<nom>-<account_id>`, accès public bloqué, versionnés, `aws:kms` + `bucket_key_enabled`, outputs `bucket_names`/`bucket_arns` en map.
  1. `modules/s3-buckets/variables.tf` : `prefix`, `suffix`, `names` (défaut les 5), `kms_key_arn`, `force_destroy` défaut `false` (sécurité par défaut, le root dit `true` en dev).
  2. `main.tf` : `aws_s3_bucket.this` avec `for_each = toset(var.names)`, `bucket = "${var.prefix}-${each.key}-${var.suffix}"`. Puis 3 réglages avec `for_each = aws_s3_bucket.this` et `bucket = each.value.id` : `public_access_block` (4 × `true`), `versioning` `Enabled`, `server_side_encryption_configuration` (`bucket_key_enabled = true` dans `rule`, `aws:kms` + `kms_master_key_id` dans le sous-bloc).
  3. `outputs.tf` : `{ for k, b in aws_s3_bucket.this : k => b.arn }` = for expression, map nom logique → ARN (≈ `Object.fromEntries(entries.map(([k,b]) => [k, b.arn]))`).
  4. Root `main.tf` : `module "s3"` avec `suffix = data.aws_caller_identity.current.account_id` (déjà dans `alerts.tf`), `kms_key_arn = module.kms.key_arn` (dépendance implicite), `force_destroy = var.environment == "dev"`. `outputs.tf` : `bucket_names`, `bucket_arns`.
  5. `make plan` → `Plan: 20 to add` ; `make up`.
- Concept : `for_each` sur un set → une instance par nom, adressée `module.s3.aws_s3_bucket.this["raw"]` ; ajouter un nom plus tard ne touche pas les autres (contrairement à `count`). Les réglages sont des ressources séparées qui référencent `aws_s3_bucket.this[each.key].id`. `force_destroy` est la seule façon pour `terraform destroy` de vider un bucket : en `dev` seulement.

## Pièges courants (dev TS → Python)
