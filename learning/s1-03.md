# S1-03 · [Python] Structure du monorepo (3 h)
Liste : S1 — Repo, Terraform, ingestion BODACC · Échéance : 2026-11-01 · Étiquettes : jaune, violet · [Carte Trello](https://trello.com/c/TqRPm5N9)

## Objectif
Monter le squelette du monorepo Python (workspace `uv`, `ruff`, `pytest`, `pre-commit`, `Makefile`) sur lequel toutes les cartes suivantes s'empilent — Pourquoi ça compte dans le projet : le client BODACC (S1-06), les Lambdas et les jobs Spark seront des membres de ce workspace ; sans structure commune, chaque brique réinvente son lint, ses tests et son packaging.

## Prérequis
### Workspaces uv
Un workspace uv ≈ `pnpm-workspace.yaml` : un `pyproject.toml` racine avec `[tool.uv.workspace] members = [...]`, un seul `uv.lock`, un seul `.venv` à la racine. Chaque membre a son propre `pyproject.toml` et devient une dépendance éditable des autres via `[tool.uv.sources] x = { workspace = true }` (≈ `"x": "workspace:*"`). `uv sync` n'installe que le graphe de la racine ; `uv sync --all-packages` installe tous les membres. `uv init` lancé dans un workspace ajoute automatiquement le nouveau projet aux membres.
Doc : https://docs.astral.sh/uv/concepts/projects/workspaces/
Exercice 5 min : dans un dossier temporaire hors du repo, `uv init --bare ws`, ajouter `[tool.uv.workspace] members = ["libs/*"]`, puis `uv init --lib libs/a` depuis `ws/`. Ouvrir `uv.lock` et retrouver l'entrée de `a` (`source = { editable = "libs/a" }`).

### pyproject.toml, PEP 621 et dependency groups
`pyproject.toml` ≈ `package.json` : `[project]` (nom, version, `requires-python`, `dependencies`), `[build-system]` (uniquement si le projet est un package installable), `[dependency-groups] dev = [...]` (PEP 735) ≈ `devDependencies`. La racine d'un monorepo n'a pas besoin d'être un package : sans `[build-system]`, uv la traite comme une « application » non installée. Les sections `[tool.*]` hébergent la config des outils (ruff, pytest), comme les clés `eslintConfig`/`jest` dans `package.json`.
Doc : https://packaging.python.org/en/latest/guides/writing-pyproject-toml/ · https://docs.astral.sh/uv/concepts/projects/dependencies/#dependency-groups
Exercice 5 min : dans le workspace de l'exercice précédent, `uv add --dev pytest` puis `git diff`-style : relire `pyproject.toml` et `uv.lock`. Où atterrit pytest ? Pourquoi pas dans `[project.dependencies]` ?

### src layout
Un package en src layout range son code dans `src/<module>/` et non à la racine du projet. Conséquence : impossible d'importer le module « par accident » depuis le cwd sans l'avoir installé, donc les tests testent la version installée (éditable) et pas un dossier qui traîne. `uv init --lib` génère ce layout avec `hatchling` comme build backend et un `py.typed`. Nom de distribution (`dp-common`, tiret) ≠ nom de module (`dp_common`, underscore) : pas de `@scope/` en Python.
Doc : https://packaging.python.org/en/latest/discussions/src-layout-vs-flat-layout/
Exercice 5 min : `uv init --lib /tmp/demo-lib` puis `tree /tmp/demo-lib` (ou `find`). Nommer chaque fichier généré et son rôle. Pourquoi `__init__.py` est dans `src/demo_lib/` et pas dans `src/` ?

### ruff : check et format
`ruff check` = eslint (règles sélectionnées par préfixe : `E` pycodestyle, `F` pyflakes, `I` isort, `UP` pyupgrade, `B` bugbear), `ruff format` = prettier (formatage, pas de règles). Une seule section `[tool.ruff]` à la racine s'applique à tout le monorepo : ruff cherche le `pyproject.toml` le plus proche qui a une section `tool.ruff` en remontant depuis chaque fichier. `ruff format` ne trie pas les imports : `I001` se corrige avec `ruff check --fix`.
Doc : https://docs.astral.sh/ruff/configuration/ · https://docs.astral.sh/ruff/rules/
Exercice 5 min : écrire un fichier avec un import inutilisé, deux imports dans le désordre et une ligne de 130 caractères. `uvx ruff check fichier.py` : trois codes différents attendus. `uvx ruff check --fix fichier.py` : lesquels restent ?

### pytest : découverte et import modes
pytest collecte les fichiers `test_*.py` ou `*_test.py` sous `testpaths`, les fonctions `test_*`, et utilise `assert` nu (introspection de l'expression à l'échec, pas de `expect().toBe()`). Dans un monorepo, deux membres qui ont chacun un `tests/test_smoke.py` sans `__init__.py` provoquent « import file mismatch » avec le mode d'import par défaut ; `--import-mode=importlib` règle ça. `rootdir` (première ligne de sortie) doit être la racine du repo pour que la config soit lue.
Doc : https://docs.pytest.org/en/stable/explanation/goodpractices.html · https://docs.pytest.org/en/stable/explanation/pythonpath.html
Exercice 5 min : créer `t/test_a.py` avec `def test_x(): assert 1 + 1 == 3`, lancer `uvx pytest t -q`. Lire la sortie : que montre pytest que Jest ne montre pas sans matcher ?

### pre-commit
pre-commit ≈ husky + lint-staged : un `.pre-commit-config.yaml` déclare des dépôts de hooks épinglés par `rev` (tag git) ; chaque hook tourne dans son propre environnement isolé, créé au premier lancement (lent une fois, puis caché dans `~/.cache/pre-commit`). Au `git commit`, seuls les fichiers stagés passent ; `pre-commit run --all-files` force tout. Si un hook modifie un fichier, le commit est annulé : re-`git add`, recommit.
Doc : https://pre-commit.com/ · https://github.com/astral-sh/ruff-pre-commit · https://github.com/astral-sh/uv-pre-commit
Exercice 5 min : lire le README de `ruff-pre-commit`. Noter les deux ids de hooks à utiliser et pourquoi l'ordre `ruff-check` puis `ruff-format` est recommandé.

- À faire : à la racine, dans l'ordre.

- Concept : la racine est le « `package.json` privé » du monorepo : pas de `[build-system]`, donc jamais installée, elle porte le lock, le venv et les deps de dev dans `[dependency-groups] dev`. - Indice : un workspace sans membre est valide, les membres arrivent à l'étape 3. `uv add --dev` écrit dans `[dependency-groups] dev`, pas dans `[project.optional-dependencies]` (différence PEP 735 vs extras : les groupes ne sont pas publiés). `uv.lock` se commite.
- Vérifier : `uv sync` → `Resolved N packages` + `.venv` créé à la racine ; `uv tree --depth 1` → `pytest`, `ruff`, `pre-commit` listés ; `ls uv.lock .venv/bin/python` → les deux présents ; `git status --short .python-version` → vide

- À faire : une seule config ruff à la racine, qui s'applique à tous les membres.
  1. Dans le `pyproject.toml` racine, section `[tool.ruff]` : `line-length = 120`, `target-version = "py312"`, `src = ["packages/*/src", "lambdas/*/src", "jobs/*/src"]`.
  2. Section `[tool.ruff.lint]` : `select = ["E", "F", "I", "UP", "B"]`.

### [x] Étape 5 — pytest : config racine et test de fumée
- À faire : config pytest à la racine, premier test qui importe un membre du workspace.
  1. Dans le `pyproject.toml` racine, section `[tool.pytest.ini_options]` : `testpaths = ["packages", "lambdas", "jobs"]`, `addopts = "-q --import-mode=importlib"`.
  2. Créer `packages/dp-common/tests/test_smoke.py` (`tests/` à côté de `src/`, pas dedans). `from dp_common import __version__, project_tag`. `test_project_tag` : `assert project_tag() == "data-platform"`. `test_version` : `assert isinstance(__version__, str)` puis `assert __version__` (chaîne vide = falsy). Pas d'`import pytest`, pas de matcher : `assert` nu, pytest réécrit l'expression et affiche les deux côtés à l'échec.
  3. `uv run pytest` → `2 passed`. Pas de `conftest.py` ni `__init__.py`.
- Concept : `testpaths` limite la collecte (pas de descente dans `infra/`, `.venv/`, `kata/`). `addopts` ≈ options par défaut toujours appliquées. `--import-mode=importlib` prépare la cohabitation de plusieurs membres avec des `tests/` homonymes sans `__init__.py` ni bidouille de `sys.path`.
- Question : pourquoi `--import-mode=importlib` dès maintenant, avec un seul membre ? → en mode par défaut (`prepend`), pytest met le dossier du test dans `sys.path` et importe `test_smoke` comme module nu. Un deuxième membre avec son `tests/test_smoke.py` = même nom, deux fichiers → `import file mismatch`. `importlib` nomme chaque fichier d'après son chemin, sans toucher `sys.path`. Posé maintenant pour ne pas le découvrir à la première Lambda.
- Erreur vue : `--collect-only -q` affiche `test_smoke.py: 2` et `head -1` affiche `..` au lieu de `rootdir` → `-q` est déjà dans `addopts`, le second donne `-qq` (ultra-compact) et supprime l'en-tête. `addopts` est invisible et toujours actif : quand une sortie pytest surprend, `-o addopts=""`.
- Indice : pas de `conftest.py` nécessaire à ce stade. Si pytest collecte 0 test, vérifie la première ligne de sortie (`rootdir` = racine du repo ? `configfile: pyproject.toml` ?) puis le nom du fichier (`test_` en préfixe).
- Vérifier : `uv run pytest` → `2 passed` ; `uv run pytest --collect-only -q` → `packages/dp-common/tests/test_smoke.py::test_project_tag` et `::test_version` ; `uv run pytest 2>&1 | head -1` → `rootdir` pointe sur la racine du repo
- Résultat : `2 passed in 0.03s`, collecte `packages/dp-common/tests/test_smoke.py: 2`. Le `-q` d'`addopts` appliqué prouve que le `pyproject.toml` racine est lu (donc rootdir correct), la collecte sous `packages/` prouve `testpaths`. `test_smoke.py` écrit par le tuteur sur « fait », relu.

### [x] Étape 6 — Makefile
- À faire : `Makefile` racine, point d'entrée unique pour le lint, le format et les tests (aucun Makefile préexistant, S1-02 n'en avait pas créé).
  1. Première ligne : `.PHONY: sync lint fmt test check`.
  2. Cinq cibles : `sync` → `uv sync --all-packages` ; `lint` → `uv run ruff check .` puis `uv run ruff format --check .` ; `fmt` → `uv run ruff format .` puis `uv run ruff check --fix .` ; `test` → `uv run pytest` ; `check: lint test` sans recette.
  3. Tabulation devant chaque ligne de recette. VS Code : « Indent Using Tabs » + fichier reconnu comme Makefile.
  4. `uv run` partout : pas d'activation du venv, marche depuis n'importe quel shell et en CI.
- Concept : Makefile ≈ `scripts` de `package.json` sans gestionnaire de paquets : recettes = lignes shell indentées par une tabulation (pas des espaces), chaque ligne tourne dans son propre shell et stoppe la recette si elle échoue. `.PHONY` déclare que la cible n'est pas un fichier : sans ça, `make test` ne fait rien le jour où un dossier `test` existe. `uv run` évite d'activer le venv.
- Question : si `ruff check` échoue dans `lint`, la ligne `ruff format --check` tourne ou pas ? → non. Chaque ligne de recette tourne dans son propre shell ; make lit le code retour et stoppe la cible au premier ≠ 0 (`make: *** [Makefile:7: lint] Error 1`). Même logique que `a && b`. Voulu : `make lint` rouge = on corrige, on ne continue pas.
- Question : `ruff check` ne vérifie pas le formatage ? → non. `ruff check` = lint (eslint : `F401`, `E501`, `I001`), `ruff format --check` = mise en forme (prettier : quotes, virgules, espaces). `x='a'` passe le lint, échoue le format. D'où deux lignes dans `lint` et deux outils dans `fmt`.
- Indice : erreur « missing separator » = espaces au lieu de tab (VS Code : regarder l'indentation en bas à droite, forcer « Indent Using Tabs » pour ce fichier). `check: lint test` suffit pour enchaîner, pas besoin de `$(MAKE) lint`.
- Vérifier : `make lint` → `All checks passed!` + `already formatted`, code retour 0 ; `make test` → `2 passed` ; `make -n check` → affiche les commandes de `lint` puis `test` sans les exécuter
- Résultat : `make lint` → `All checks passed!` + `17 files already formatted` (16 + `test_smoke.py`), `rc=0` ; `make test` → `2 passed in 0.02s` ; `make -n check` → les 3 commandes listées, rien exécuté. Makefile écrit par le tuteur sur « fait le », relu.

### [x] Étape 7 — pre-commit
- À faire : hooks git qui refusent tout commit non formaté, non linté ou avec un lock désaligné.
  1. `.pre-commit-config.yaml` racine, trois `repos` (`repo`, `rev`, `hooks`) : `pre-commit/pre-commit-hooks` `rev: v6.0.0` (`trailing-whitespace`, `end-of-file-fixer`, `check-yaml`, `check-toml`, `check-added-large-files`) ; `astral-sh/ruff-pre-commit` `rev: v0.17.1` = ruff du lock (`ruff-check` avec `args: [--fix]`, puis `ruff-format`) ; `astral-sh/uv-pre-commit` `rev: 0.9.28` = `uv --version` local, sans `v` (`uv-lock`). Tags trouvés avec `git ls-remote --tags --refs <repo>`.
  2. `uv run pre-commit install` → écrit `.git/hooks/pre-commit`. Le YAML est relu à chaque lancement, pas à l'install.
  3. `uv run pre-commit run --all-files`. Première fois lente : clone de chaque dépôt au `rev`, un env isolé par dépôt dans `~/.cache/pre-commit`.
  4. Si un hook `Failed` en modifiant un fichier (`files were modified by this hook`) : `git add <fichier>`, relancer. Au second tour `Passed`.
- Concept : chaque dépôt est épinglé par `rev` et tourne dans un env isolé, indépendant du `.venv` : la version de ruff du hook est celle du `rev`, pas celle de `uv.lock`. `uv-lock` refuse le commit si `uv.lock` n'est plus aligné sur les `pyproject.toml`. Ordre `ruff-check --fix` avant `ruff-format` : le fix peut déformater, le format repasse derrière.
- Question : le ruff du hook (`rev`) et celui du `.venv` (`uv.lock`) divergent, qu'est-ce qui casse ? → deux installations : `make lint` passe et le hook échoue, ou l'inverse. Pire avec `uv-lock` : un uv plus récent dans le hook réécrit `uv.lock` à chaque commit. D'où `rev` aligné sur le lock pour ruff et sur `uv --version` pour uv.
- Erreur vue : premier `--all-files` → `ruff check`, `check toml`, `uv-lock` en `(no files to check) Skipped`, rc=0 → faux vert. `--all-files` = fichiers **suivis par git** (`git ls-files`), tout le scaffold était encore `??`. Fix : `git add` ciblé des fichiers voulus, relance → tous `Passed`. Au `git commit`, même règle : seuls les fichiers stagés passent dans les hooks.
- Erreur vue : `fix end of files Failed … Fixing pyproject.toml` → le hook a ajouté le retour à la ligne final et se déclare `Failed` parce qu'il a modifié un fichier. Contrat voulu : rien ne part sans relecture. `git add pyproject.toml`, relance → `Passed`.
- Indice : aligne le `rev` de `ruff-pre-commit` sur la version de ruff visible dans `uv tree` (ex. ruff 0.14.x → `rev: v0.14.x`). Les ids actuels sont `ruff-check` et `ruff-format` (`ruff` seul est l'ancien alias). Première exécution lente (création des envs) : normal.
- Vérifier : `uv run pre-commit run --all-files` → chaque hook `Passed` ou `Skipped`, code retour 0 ; `ls .git/hooks/pre-commit` → fichier présent ; `uv run pre-commit run --all-files --verbose ruff-check` → version de ruff identique à celle de `uv tree`
- Résultat : 8 hooks `Passed`, `rc=0`, `.git/hooks/pre-commit` présent. Au quotidien : `git add` + `git commit` normaux ; hook qui corrige = commit annulé, re-`git add`, recommit ; `make fmt` avant pour éviter le tour supplémentaire. YAML écrit par le tuteur sur « fait le », relu.

## Question de compréhension
Un seul `uv.lock` et un seul `.venv` à la racine pour tout le monorepo, alors que chaque Lambda partira en prod avec son propre zip de dépendances : quel problème ça pose au moment du packaging d'une Lambda (taille, dépendances inutiles, versions), et avec quelle(s) commande(s) uv tu extrairais uniquement le graphe de `lambdas/<x>` sans ses deps de dev ?
Réponse (donnée par le tuteur sur demande, 2026-10-22) :
- Problème : le `.venv` racine contient tout (pytest, ruff, pyspark demain). Zippé tel quel : limite Lambda 250 Mo décompressé dépassée, cold start allongé, deps inutiles embarquées. Le lock unique impose une seule résolution de versions pour tous les membres : cohérent, mais à savoir si une Lambda a besoin d'un pin différent.
- Commandes : `uv export --package <lambda> --no-dev --no-emit-workspace --format requirements.txt -o requirements.txt` puis `uv pip install -r requirements.txt --target build/ --python-platform x86_64-manylinux2014 --python-version 3.12`. Alternative : `uv sync --package <lambda> --no-dev --no-editable` dans un venv jetable. Même lock qu'en local → zip reproductible.
