# revision-pwa · app de révision multi-projets
Liste : S1 (carte `pwa-revision`, board `fMaiYRrn`) · Échéance : aucune · Étiquettes : front, Terraform, AWS, CI, agent

## Objectif
Une seule app de révision pour tous les projets : la PWA React (cartes swipables façon TikTok, langage > thème > sous-thème) vit dans son propre dépôt privé `revision-pwa` (AWS CodeCommit, à côté de `data-platform` dans `workspace/`), avec son infra Terraform (S3 privé + CloudFront OAC). Les projets **producteurs** (aujourd'hui `data-platform`, demain d'autres) ne livrent que des fichiers `cartes-*.md`, écrits par **un seul agent** (`/cartes`) qui suit une spécification précise (`spec/cartes.md`), et les poussent dans un bucket S3 de contenu ; l'app les lit à l'exécution via un catalogue reconstruit par une Lambda — Pourquoi ça compte : la révision ne dépend plus d'un dépôt ni d'un redéploiement de l'app, et le schéma producteur → S3 → Lambda → consommateur est exactement celui d'un pipeline data (contrat de format, zone brute, zone publiée).

### Décisions du 2026-10-24
- **Dépôt séparé `revision-pwa`** : l'app n'est pas une brique de la plateforme data ; elle sert à plusieurs projets. Le dépôt `data-platform` ne garde que ses cartes (`learning/cartes-*.md`) et une cible `make cards-publish`.
- **`data-platform` reste sur GitHub (public)** : la roadmap repose dessus (repo public vitrine S1-01 / S8, 20 issues + PR S3-06, GitHub Actions S3-07 et S6-06, outils de l'agent `git_log` via l'API GitHub S4-03 et `open_github_issue` S5-04). CodeCommit n'a ni dépôt public ni issues : y migrer obligerait à réécrire 6 cartes et à perdre la vitrine.
- **`revision-pwa` sur CodeCommit (privé)** : outil perso, comme la plupart des dépôts de Fraoucene ; CodeCommit, fermé aux nouveaux clients en juillet 2024, est revenu en disponibilité générale le 24 novembre 2025 (https://aws.amazon.com/blogs/devops/aws-codecommit-returns-to-general-availability). CI = **CodeBuild** déclenché par EventBridge sur push `main` (pas de CodePipeline : une seule étape), identifiants par rôle de service, aucune clé.
- **Contrat de contenu** : `s3://<content>/sources/<projet>/cartes-*.md` (brut, écrit par le producteur) → Lambda `catalog-build` → `content/catalog.json` (publié, lu par l'app via CloudFront). Une carte invalide est rejetée par la Lambda, le dernier catalogue valide reste en ligne.
- **Un seul agent** : skill Claude Code `cartes` versionnée dans `revision-pwa/agent/`, liée dans `~/.claude/skills/`, utilisable depuis n'importe quel projet ; elle écrit selon `spec/cartes.md` et exécute chaque exemple avant de rendre la main. Les leçons longues (`cours-*.md`) suivront le même circuit plus tard.

## Prérequis
### Vite + React + TypeScript dans un monorepo Python
Vite ≈ le serveur de dev et le bundler de Next sans le serveur : `pnpm create vite` génère une SPA statique (`index.html` + `assets/`) que n'importe quel hébergement de fichiers sert. L'app vit dans `apps/revision/` avec son propre `package.json`, à côté du workspace uv qui ne la voit pas (uv ne lit que `packages/*`, `lambdas/*`, `jobs/*`). Node s'installe depuis nodejs.org (LTS) ou via un gestionnaire de versions ; pnpm s'active avec `corepack enable` (corepack est livré avec Node).
Doc : https://vite.dev/guide/ · https://nodejs.org/en/download · https://pnpm.io/installation#using-corepack
Exercice 5 min : dans un dossier temporaire, `pnpm create vite demo --template react-ts`, puis `pnpm install` et `pnpm build` : ouvrir `demo/dist/` et noter ce qui est produit (un `index.html`, des fichiers hachés dans `assets/`).

### Le contrat des cartes : `cartes-*.md` (spécification `spec/cartes.md`)
L'agent `/cartes` écrit les cartes dans le projet producteur ; depuis le 2026-10-24 l'app les lit **à l'exécution** via `content/catalog.json` (étapes 1-6 : lues au build depuis `learning/`). Un fichier `cartes-<langage>-<thème>.md` = un thème (`langage:` et `cours:` dans l'en-tête), une section `## N. Titre` = une carte, avec `- Sous-thème :`, `- Question :`, `- Essentiel :`, puis le corps (texte + blocs de code). Le script de build transforme ces fichiers en `cards.json` et **échoue** sur une carte incomplète : un contrat vérifié vaut mieux qu'une carte cassée sur le téléphone.
Doc : https://github.com/remarkjs/react-markdown · https://github.com/remarkjs/remark-gfm
Exercice 5 min : ouvrir `learning/cartes-python-decorateurs.md` et repérer pour une carte les 4 morceaux que le parser devra extraire (titre, Sous-thème, Question, Essentiel) et ce qui reste comme corps.

### Défilement plein écran façon TikTok en CSS
Pas besoin de librairie : un conteneur `overflow-y: scroll` + `scroll-snap-type: y mandatory`, des enfants `height: 100dvh` + `scroll-snap-align: start`. `100dvh` (dynamic viewport) suit la barre d'adresse de Safari iOS, contrairement à `100vh`. Une carte trop longue défile à l'intérieur (`overflow-y: auto`) sans casser l'aimantation.
Doc : https://developer.mozilla.org/fr/docs/Web/CSS/scroll-snap-type · https://developer.mozilla.org/fr/docs/Web/CSS/length#unités_relatives_à_la_zone_daffichage_dynamique
Exercice 5 min : dans le projet `demo`, 5 `<section>` de couleurs différentes avec les 3 propriétés ci-dessus ; tester dans le navigateur en mode mobile (DevTools) que chaque swipe s'arrête net sur une section.

### PWA : manifest + service worker
Une PWA = un site + un `manifest.webmanifest` (nom, icônes, `display: standalone`) + un service worker qui met les fichiers en cache pour le hors-ligne. Sur iPhone, Safari → Partager → « Sur l'écran d'accueil » l'installe comme une app, sans App Store. `vite-plugin-pwa` génère manifest et service worker au build (Workbox sous le capot).
Doc : https://vite-pwa-org.netlify.app/guide/ · https://developer.mozilla.org/fr/docs/Web/Progressive_web_apps
Exercice 5 min : sur un site PWA connu depuis l'iPhone, l'ajouter à l'écran d'accueil, le lancer en mode avion : noter ce qui marche hors ligne.

### S3 privé + CloudFront + OAC
CloudFront ≈ le CDN de Vercel devant tes fichiers. Le bucket S3 reste **privé** (blocage d'accès public) ; seule la distribution CloudFront peut le lire, grâce à l'Origin Access Control (OAC) : une politique de bucket qui autorise le principal `cloudfront.amazonaws.com` **pour cette distribution seulement** (`AWS:SourceArn`). Sans domaine perso, l'URL est `https://dxxxx.cloudfront.net`, certificat HTTPS inclus, donc pas d'ACM ni de Route 53.
Doc : https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html · https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/cloudfront_origin_access_control
Exercice 5 min : dans la console AWS, ouvrir CloudFront → Create distribution, choisir un bucket S3 comme origine sans valider : lire les options « Origin access » et noter la différence entre « Public », « Legacy OAI » et « Origin access control ».

### CI sans clé : rôle de service CodeBuild et OIDC GitHub
Deux CI, deux mécanismes, aucune clé stockée. `revision-pwa` (CodeCommit) : une règle EventBridge sur l'événement `referenceUpdated` de `main` démarre un projet CodeBuild, qui tourne avec son **rôle de service** IAM (build, `s3 sync`, invalidation). `data-platform` (GitHub) : pour publier ses cartes, GitHub Actions obtient des identifiants AWS **temporaires** sans clé stockée : AWS fait confiance au fournisseur OIDC `token.actions.githubusercontent.com` et à un rôle IAM dont la politique de confiance ne laisse entrer que ce dépôt et cette branche (`sub = repo:<owner>/<repo>:ref:refs/heads/main`), limité à `sources/data-platform/*`.
Doc : https://docs.aws.amazon.com/codebuild/latest/userguide/sample-codecommit.html · https://docs.aws.amazon.com/codecommit/latest/userguide/monitoring-events.html
Doc : https://docs.github.com/fr/actions/security-for-github-actions/security-hardening-your-deployments/configuring-openid-connect-in-amazon-web-services · https://github.com/aws-actions/configure-aws-credentials
Exercice 5 min : lire le schéma du lien GitHub ci-dessus et écrire en une phrase pourquoi aucun secret AWS n'est stocké dans GitHub.

### [x] Étape 3 — Contrôle d'exécution des exemples Python
- À faire :
  1. `apps/revision/scripts/check_cards.py` → `extract_blocks` : même automate que le parser TS (`in_fence`), ne garde que les blocs `python`, retient la ligne `.md` de départ.
  2. `ast.parse(bloc)` → une instruction de premier niveau à la fois (`ast.Module([stmt], [])`), `end_lineno` = ligne qui porte le `# →`.
  3. Annotée `# →` : `eval` de l'expression puis comparaison ; `# ❌ Nom` : `exec`, doit lever `Nom` (cherché dans `__mro__`) ; sinon `exec`.
  4. Valeur attendue : `ast.literal_eval`, sinon `eval` dans l'espace de noms de la carte (`str`, `Page(...)`) ; suffixe ` : …` / `  (…)` retiré ; rien d'évaluable = commentaire ignoré.
  5. Erreur inattendue → un échec et arrêt du bloc (pas de cascade) ; `print` avalés (`redirect_stdout`).
  6. `Makefile` : cible `cards-check` (+ `.PHONY`) → `uv run python apps/revision/scripts/check_cards.py`.
- Concept : c'est quoi : un test de documentation (≈ `doctest`), pour que chaque exemple soit vrai. Pourquoi ici : la relecture du 2026-10-23 a trouvé 6 cartes de décorateurs non exécutables seules (dépendance entre cartes, imports manquants) ; ce contrôle les attrape avant le téléphone. Objectif : un rapport carte par carte, et un code de sortie ≠ 0 tant qu'une carte échoue.
- Indice : `ast.parse` du bloc, puis exécuter instruction par instruction dans un dict `ns` neuf par bloc ; `eval` pour une expression, `exec` pour le reste. Les commentaires descriptifs (`# → l'objet a`) ne sont pas des valeurs : ne comparer que ce qui s'évalue (`ast.literal_eval`), sinon ignorer.
- Vérifier : `make cards-check` → `0 échec`, code de sortie `0` ; changer un `# →` d'une carte → la carte est signalée, code de sortie ≠ 0 ; `uv run ruff check apps/revision/scripts` → `All checks passed!`
- Cours : `eval` = une expression → une valeur ; `exec` = n'importe quelle instruction → rien. Python distingue expression et instruction (`x = 1` n'a pas de valeur), JS beaucoup moins.
- Cours : `ast.literal_eval` n'évalue que des littéraux (listes, dicts, nombres, chaînes, `None`) : sûr ; `eval` exécute du code arbitraire, acceptable ici car le code vient du dépôt.
- Cours : espace de noms neuf par bloc (`ns = {"__name__": "__carte__"}`) → une carte qui dépend d'une autre échoue en `NameError`, le défaut visé.
- Cours : `warning: VIRTUAL_ENV=…pyenv… does not match` : pyenv exporte `VIRTUAL_ENV`, uv l'ignore et prend `.venv` ; sans effet.
- Résultat : `39 blocs, 100 vérifications, 0 commentaires ignorés, 0 échec(s)`, code `0` ; ruff vert ; mutations (`# → 5` → `6`, `s[5]` → `s[0]` sous `# ❌ IndexError`) → `ÉCHEC …decorateurs.md:4 (Écrire le sien : un chrono) ligne 104 : attendu 6, obtenu 5` et `ÉCHEC …collections.md:2 (list : lire) ligne 44 : attendu ❌ IndexError, rien levé`, code `1` ; fichiers restaurés (`cmp`).

## Pièges courants (dev TS → Terraform / AWS)
1. Bucket S3 public + CloudFront : inutile et risqué ; garder les buckets privés, accès par OAC uniquement (`AWS:SourceArn`).
2. Clé KMS sur les buckets du site : CloudFront ne peut pas déchiffrer sans modifier la politique de la clé ; SSE-S3 suffit pour des fichiers publics par nature.
3. SPA sur CloudFront : une réponse personnalisée 403/404 → `/index.html` vaut pour toute la distribution, `/content/*` compris (un catalogue absent renvoie du HTML au `fetch`) ; inutile ici, l'app n'a qu'une page (navigation par query).
4. `index.html`, `sw.js` ou `catalog.json` mis en cache longtemps : l'app ou les cartes ne se mettent jamais à jour ; seuls les fichiers hachés sont immuables.
5. Service worker testé via l'IP locale : il ne s'enregistre qu'en HTTPS ou sur `localhost` ; tester le hors-ligne après déploiement.
6. Lambda déclenchée sur le préfixe où elle écrit : boucle infinie et facture ; entrée `sources/`, sortie `content/`.
7. OIDC sans condition `sub` précise : n'importe quel dépôt GitHub pourrait endosser le rôle ; restreindre au dépôt et à la branche, et le préfixe S3 au projet.
8. `aws s3 sync --delete` sur le mauvais bucket ou sans `--exclude` : efface l'app ou les cartes des autres projets ; noms toujours depuis `terraform output`.
9. Deux formats de cartes qui divergent : la spec `spec/cartes.md` est la seule référence ; parser, Lambda et agent la suivent.
