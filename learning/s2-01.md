## Prérequis
### JVM, PySpark et Py4J
Spark est écrit en Scala et tourne dans une JVM. PySpark est un client Python qui pilote cette JVM par Py4J (un pont RPC local) : `import pyspark` ne suffit pas, il faut un JDK (17 pour Spark 3.5) et `JAVA_HOME`. Le premier `SparkSession.builder.getOrCreate()` démarre la JVM (2 à 5 s) : à faire une fois par session de tests, pas par test. ≈ un client Node qui lancerait un serveur Java en sous-processus et lui parlerait par socket.
Doc : https://spark.apache.org/docs/3.5.8/api/python/getting_started/install.html
Exercice 5 min : expliquer pourquoi `pip install pyspark` réussit sur une machine sans Java, et à quel moment précis l'erreur apparaîtra.

### SparkSession, `local[n]`, transformations et actions
`SparkSession` = point d'entrée (≈ un client de base de données). `master("local[1]")` : tout dans un processus, 1 thread de calcul. Un DataFrame est une **requête différée**, pas un tableau en mémoire : `select`, `filter`, `withColumn` construisent un plan (transformations) ; rien n'est lu avant une action (`count`, `collect`, `show`, `write`). ≈ un query builder (Drizzle, Knex) avant `await`.
Doc : https://spark.apache.org/docs/3.5.8/api/python/getting_started/quickstart_df.html
Exercice 5 min : dans `spark.read.json(chemin).filter(...).select(...)`, quelle ligne lit le fichier ? Et si le fichier n'existe pas, quelle ligne lève l'erreur ?

### Schéma explicite (`StructType`) contre inférence
`spark.read.json` sans schéma lit tout le fichier pour deviner les types (`inferSchema`) : lent, et le schéma change selon les données du jour (champ toujours `null` → type `string` ou absent, journée vide → DataFrame sans colonnes). En production on passe `.schema(...)` : types stables, colonnes présentes même vides. `StructType` / `StructField` ≈ un schéma zod côté Spark ; `from_json(col, schema)` ≈ `JSON.parse` + validation d'un champ texte.
Doc : https://spark.apache.org/docs/3.5.8/sql-data-sources-json.html
Exercice 5 min : citer deux champs BODACC qui sont du JSON dans une chaîne (voir `docs/source-bodacc.md` §5) et dire ce que Spark en ferait sans `from_json`.

### Iceberg et catalogue Hadoop
Iceberg = format de table sur des fichiers Parquet : un journal de métadonnées (snapshots) rend les écritures atomiques, permet `MERGE`, l'évolution de schéma et le voyage dans le temps. Un **catalogue** dit où trouver la métadonnée courante d'une table : en prod ce sera Glue (S2-03), en test le type `hadoop` (un simple dossier). Spark le charge par un jar (`iceberg-spark-runtime`) et des clés `spark.sql.catalog.<nom>.*`.
Doc : https://iceberg.apache.org/docs/1.11.0/spark-configuration/
Exercice 5 min : citer ce que Iceberg ajoute au couple « Parquet + `_MANIFEST.json` » de S1-07 (voir la question de compréhension de S1-07, point 4).

### sparkdantic : un modèle Pydantic, deux schémas
`class Event(SparkModel)` est un `BaseModel` Pydantic normal (validation, `model_validate`) qui sait en plus produire son `StructType` (`Event.model_spark_schema()`). Les types se traduisent : `str` → `StringType`, `date` → `DateType`, `datetime` → `TimestampType`, `list[Person]` → `ArrayType(StructType)`, `X | None` → colonne nullable. ≈ un schéma zod dont on dériverait aussi le DDL SQL.
Doc : https://github.com/mitchelllisle/sparkdantic
Exercice 5 min : prédire la nullabilité de `siren: str` et de `tribunal: str | None` dans le `StructType` produit.

### [x] Étape 6 — Job `jobs/normalize/` : raw → DataFrame d'événements typé
- À faire : c'est quoi : le premier job Spark du projet, en fonction pure `normalize(raw_df, ingested_at) -> DataFrame`. Pourquoi ici : S2-02 y mettra les règles fines, S2-04 l'enverra sur EMR ; la forme (fonction pure + petit `main`) ne bougera plus. Objectif : la sortie a exactement `Event.model_spark_schema()`.

  2. `src/bodacc_normalize/transform.py` (après refactor, voir Erreur vue) : `from_json` de `listepersonnes`, `personne` objet **ou** liste ramené à une liste, un événement par SIREN (`explode`), `event_type = familleavis` (affiné en S2-02), `event_date = dateparution` provisoire, `source_id = id`, `ingested_at` passé en paramètre (pas d'horloge dans la fonction).
  3. `main.py` : point d'entrée `spark-submit` (`argparse --input`, session, lecture, normalisation, log du nombre d'événements) ; l'écriture Iceberg arrive en S2-03.
- Concept : transformations Spark SQL (`from_json`, `explode`, `struct`, `cast`), fonction pure testable, horloge injectée.
- Indice : `personne` objet ou liste : essayer les deux schémas avec `from_json` et prendre celui qui n'est pas `null` (`F.coalesce`), ou tester le premier caractère. `explode` supprime les lignes à tableau vide : `explode_outer` les garde (siren `null`). Dernière étape : `df.select([F.col(f.name).cast(f.dataType) for f in schema])` aligne ordre et types.
- Vérifier : `uv run pytest jobs/normalize -q` → `passed` ; `uv run ruff check jobs` → `All checks passed!`
- Question : `coalesce` ? → première valeur non `null` parmi ses arguments, ligne par ligne (≈ `a ?? b ?? c`, `COALESCE` SQL) ; si le dernier argument ne peut pas être `null` (`lit`, `array()`), la colonne devient non nullable.
- Cours : décision nullabilité (mesurée, Spark 3.5.8) : une colonne calculée est nullable ; `df.to(schema)` refuse nullable → non nullable (`[NULLABLE_COLUMN_OR_FIELD]`), même après `filter(x is not null)` ; `coalesce(x, lit(""))` rend non nullable mais invente une valeur. Retenu : le DataFrame a noms, ordre et types d'`Event` (même `simpleString()`, qui ignore la nullabilité) ; Pydantic vérifie chaque ligne dans les tests (étape 7) ; la table Iceberg déclarera `NOT NULL` (S2-03). Seule exception : `persons = coalesce(…, array())`, liste vide = vraie valeur.

## Pièges courants (dev TS → Python / Spark)
1. Lire un DataFrame comme un tableau : `df.filter(...)` ne fait rien ; l'erreur d'un mauvais nom de colonne arrive à l'analyse, celle d'une donnée invalide seulement à l'action (`count`, `collect`).
2. `spark.read.json` sans schéma : types devinés à chaque lecture, une journée à 0 annonce donne un DataFrame sans colonnes, et la normalisation plante sur la colonne manquante.
3. Créer une `SparkSession` par test : 3 à 5 s de JVM à chaque fois, `make test` explose le budget de 60 s.
4. `spark.jars.packages` dans la fixture : téléchargement Maven au premier lancement (réseau dans les tests, CI lente, échec hors ligne).
5. `listepersonnes.personne` objet **ou** liste : un seul schéma `from_json` rend `null` pour l'autre forme, sans erreur ; l'annonce perd son SIREN en silence.
6. `explode` au lieu de `explode_outer` : les annonces sans personne disparaissent du résultat, sans erreur.
7. PySpark 4.x en local, Spark 3.5 sur EMR : API et comportements différents (ANSI activé par défaut en 4.0) ; le test vert en local ne prouve rien en prod.
8. Horodatage : la JVM prend le fuseau du Mac ; sans `spark.sql.session.timeZone=UTC`, un `timestamp` affiché ou converti change d'un poste à l'autre.
