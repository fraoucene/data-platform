# S1-02 · Garde-fous de coût (1 h)
Liste : S1 — Repo, Terraform, ingestion BODACC · Échéance : 2026-11-01 · Étiquettes : vert (sans nom) · [Carte Trello](https://trello.com/c/PAMgFZCn)

## Objectif
Poser dans `infra/` (Terraform, état local pour l'instant) un budget AWS mensuel avec alertes à 50 % et 90 % qui arrivent vraiment dans ta boîte mail, et rendre le tag `project=data-platform` impossible à oublier : `default_tags` du provider + une validation qui fait échouer `make plan` — Pourquoi ça compte dans le projet : EMR, Step Functions et Bedrock facturent vite sur un compte perso ; le tag est la seule clé qui permettra de ventiler le coût par brique (Cost Explorer filtré `project`) et de retrouver tout ce que la plateforme a créé.

Les deux critères d'acceptation viennent de la carte. Deux critères intermédiaires sont déduits du Détail et marqués comme tels.

Hypothèses : profil AWS CLI et user IAM admin de S1-01 (`--profile <profil S1-01>` ou `AWS_PROFILE` exporté) ; Terraform ≥ 1.9 installé (S1-01 étape 7, validée). Région de travail : `eu-west-3` (Paris) sauf avis contraire ; AWS Budgets est un service global, le provider gère l'endpoint.

## Prérequis
### AWS Budgets
Un budget `COST` mensuel compare la dépense réelle (`ACTUAL`) ou prévue (`FORECASTED`) à un plafond, et déclenche des notifications par seuil (`threshold` en % ou en montant). Le plafond est **en USD uniquement** : 30 € ≈ 33 à 35 USD selon le taux, tu choisis la valeur. Les données de coût arrivent avec 8 à 24 h de latence : un budget ne déclenche jamais en temps réel. Les budgets sans « actions » sont gratuits. Les destinataires sont des emails directs ou des topics SNS.
Doc : https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-managing-costs.html · https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/budgets_budget
Exercice 5 min : dans la doc de la ressource Terraform, lister les champs obligatoires d'un bloc `notification` et la différence `notification_type = "ACTUAL"` vs `"FORECASTED"`.

### SNS : topic, abonnement email, policy pour un principal de service
Pour qu'un budget publie sur un topic SNS, la **topic policy** doit autoriser le principal `budgets.amazonaws.com` à faire `SNS:Publish` sur l'ARN du topic. Un abonnement `email` reste `PendingConfirmation` tant que tu n'as pas cliqué le lien reçu : un budget qui publie sur un topic non confirmé ne produit rien, silencieusement. Ce mail de confirmation est ton premier « email de test » ; `aws sns publish` est le second.
Doc : https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-sns-policy.html · https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/sns_topic_policy
Exercice 5 min : lire la page « SNS policy for budgets » et noter la `Condition` recommandée (`aws:SourceAccount` / `aws:SourceArn`) qui empêche un budget d'un autre compte de publier chez toi.

### `default_tags` et `tags_all`
`provider "aws" { default_tags { tags = {…} } }` injecte les tags sur toute ressource taggable ; l'attribut calculé `tags_all` = fusion `default_tags` + `tags` de la ressource, **la ressource gagne** en cas de conflit (donc `tags = { project = "autre" }` écrase silencieusement). Quelques ressources ne les reçoivent pas (ex. `aws_autoscaling_group`, certains tags propagés). ≈ un `baseTags` fusionné dans chaque resource, où l'override local n'est pas une erreur. D'où le besoin d'une validation séparée.
Doc : https://registry.terraform.io/providers/hashicorp/aws/latest/docs/guides/resource-tagging
Exercice 5 min : dans le guide, retrouver la section sur `ignore_tags` et expliquer en une ligne quand on s'en sert (tags posés par un autre outil, ex. Backup, qu'il ne faut pas « corriger »).

### Validation de variable et plan JSON
`variable "x" { validation { condition = …; error_message = "…" } }` fait échouer `plan` dès l'entrée ; depuis Terraform 1.9 la `condition` peut référencer d'autres variables et des fonctions. ≈ `zod` sur les inputs du module. Pour vérifier le **résultat** du plan (toutes les ressources, `tags_all` compris), `terraform show -json tfplan` expose `planned_values.root_module.resources[].values.tags_all` et des `child_modules` récursifs : un petit script stdlib Python peut l'auditer et sortir en code 1.
Doc : https://developer.hashicorp.com/terraform/language/values/variables#custom-validation-rules · https://developer.hashicorp.com/terraform/internals/json-format
Exercice 5 min : dans la page « JSON Output Format », repérer où vit `tags_all` d'une ressource planifiée et comment un module enfant apparaît (`child_modules[].resources`).

## Étapes

### [ ] Étape 1 — Squelette `infra/` et provider avec `default_tags`
- À faire : créer `infra/` à la racine (c'est le dossier que S1-03 attend). `infra/versions.tf` : `required_version = ">= 1.9"`, provider `hashicorp/aws` `~> 6.0`. `infra/providers.tf` : `provider "aws"` avec `region = var.region` et `default_tags { tags = var.tags }`. `infra/variables.tf` : `region` (default `eu-west-3`), `tags` (`map(string)`, default `{ project = "data-platform" }`), `alert_email` (`string`, sensitive = false, sans défaut : passé en `-var` ou `TF_VAR_alert_email`, **jamais** commité), `budget_limit_usd` (`number`, default `35`). Pas de backend distant pour l'instant : état local, déjà ignoré par `.gitignore`.
- Concept : contraintes de version, `default_tags`, variables typées, séparation valeurs sensibles / code.
- Indice : l'email dans un `.tfvars` ignoré par git (`*.tfvars` est dans le `.gitignore` de S1-01) ou en `TF_VAR_alert_email`. Pas en `default`.
- Vérifier : `terraform -chdir=infra init` puis `terraform -chdir=infra validate` → `Success! The configuration is valid.` ; `git status --short infra` ne montre ni `.terraform/` ni `*.tfvars`.

### [ ] Étape 2 — Validation de la variable `tags`
- À faire : dans `variables.tf`, ajouter à `tags` un bloc `validation` qui exige `lookup(var.tags, "project", "") == "data-platform"` avec un `error_message` explicite. Tester l'échec en passant une map vide.
- Concept : validation à l'entrée (≈ `zod.parse` sur les inputs), `lookup` avec défaut, échec au `plan` avant tout appel AWS.
- Indice : la validation ne vérifie que la **variable**, pas ce qu'une ressource peut écraser localement. C'est la première barrière ; l'étape 5 est la seconde.
- Vérifier : `terraform -chdir=infra plan -var='tags={}' -var='alert_email=x@y.z'` → erreur « Invalid value for variable » avec ton message ; sans l'override → plan passe (0 ressource).

### [ ] Étape 3 — Topic SNS, abonnement email, policy pour `budgets.amazonaws.com`
- À faire : `infra/alerts.tf` : `aws_sns_topic` (`name = "data-platform-budget-alerts"`), `aws_sns_topic_subscription` (`protocol = "email"`, `endpoint = var.alert_email`), `aws_sns_topic_policy` avec un `data "aws_iam_policy_document"` : `Allow` `sns:Publish` au principal service `budgets.amazonaws.com` sur l'ARN du topic, condition `aws:SourceAccount` = ton compte (via `data "aws_caller_identity"`). `terraform apply`. Cliquer le lien dans le mail « AWS Notification - Subscription Confirmation ».
- Concept : topic policy vs IAM policy (le producteur est un service, pas un rôle), `data` sources, confirmation d'abonnement email.
- Indice : un abonnement `email` ne peut pas être confirmé par Terraform ; l'attribut `pending_confirmation` ou `aws sns list-subscriptions-by-topic` te dira s'il l'est. Tant que c'est `PendingConfirmation`, rien ne sortira.
- Vérifier : `aws sns list-subscriptions-by-topic --topic-arn $(terraform -chdir=infra output -raw budget_topic_arn) --query 'Subscriptions[].SubscriptionArn'` → un ARN complet, pas `PendingConfirmation` ; puis `aws sns publish --topic-arn $(terraform -chdir=infra output -raw budget_topic_arn) --subject "test budget" --message "ok"` → mail reçu. **Critère « Email de test reçu » validé.**

### [ ] Étape 4 — Le budget : 30 €/mois, alertes 50 % et 90 %
- À faire : `infra/budget.tf` : `aws_budgets_budget` `budget_type = "COST"`, `time_unit = "MONTHLY"`, `limit_amount = var.budget_limit_usd`, `limit_unit = "USD"`, deux blocs `notification` : `comparison_operator = "GREATER_THAN"`, `threshold_type = "PERCENTAGE"`, `notification_type = "ACTUAL"`, `threshold = 50` puis `90`, `subscriber_sns_topic_arns = [topic]` et, en ceinture, `subscriber_email_addresses = [var.alert_email]`. Un `output "budget_topic_arn"`. `terraform apply`.
- Concept : budget global, seuils en %, double canal (SNS testable + email direct sans dépendance), `limit_amount` en chaîne côté API.
- Indice : si l'apply échoue sur `AccessDenied` à `budgets:*`, c'est le user IAM, pas Terraform ; si c'est `InvalidParameter` sur le topic, relis la topic policy de l'étape 3. Tu peux aussi ajouter un troisième seuil `FORECASTED 100` : AWS te prévient avant de dépasser, pas après.
- Vérifier : `aws budgets describe-budget --account-id $(aws sts get-caller-identity --query Account --output text) --budget-name data-platform-monthly --query 'Budget.BudgetLimit'` → `{"Amount": "35.0", "Unit": "USD"}` ; `aws budgets describe-notifications-for-budget --account-id … --budget-name data-platform-monthly --query 'Notifications[].Threshold'` → `[50.0, 90.0]`. **Critère déduit « budget + 2 seuils » validé.**

### [ ] Étape 5 — Audit du plan en Python : `infra/scripts/check_tags.py`
- À faire : script stdlib (bloc PEP 723, `requires-python = ">=3.12"`, zéro dépendance) qui lit le JSON de `terraform show -json tfplan` sur `stdin`, parcourt `planned_values.root_module` **et** ses `child_modules` récursivement, et pour chaque ressource dont `values` contient la clé `tags_all`, exige `tags_all["project"] == "data-platform"`. Affiche les adresses fautives (`aws_s3_bucket.raw`), sort en `1` s'il y en a, `0` sinon. Test négatif : ajouter temporairement une `aws_sns_topic` « test » avec `tags = { project = "oops" }`, constater l'échec, la retirer.
- Concept : `json.load(sys.stdin)`, récursion sur une structure d'arbre, `dict.get(…) or {}` (`tags_all` peut valoir `null`), `sys.exit(code)`. Exercice Py S1 appliqué : un vrai script d'outillage, écrit sans IA.
- Indice : les ressources `data` apparaissent aussi dans `planned_values` avec `mode = "data"` : décide si tu les ignores. Et `tags_all` est absent (pas `null`) sur les ressources non taggables : `"tags_all" in values` est le bon test.
- Vérifier : `terraform -chdir=infra plan -out=tfplan && terraform -chdir=infra show -json tfplan | uv run infra/scripts/check_tags.py; echo "exit=$?"` → `exit=0` ; avec la ressource « oops » → la ligne fautive et `exit=1`. **Critère « `terraform plan` échoue si une ressource n'a pas le tag » validé** (via la cible `make plan`, étape 6).

### [ ] Étape 6 — `make plan` et commit
- À faire : `Makefile` racine (S1-03 l'étendra) avec une cible `plan` qui enchaîne `terraform -chdir=infra plan -out=infra/tfplan` puis `terraform -chdir=infra show -json infra/tfplan | uv run infra/scripts/check_tags.py` ; `.PHONY`. Ajouter `tfplan` et `infra/tfplan` au `.gitignore`. Vérifier qu'aucun état, plan ou `.tfvars` n'est suivi. Commit préfixé `main: ` (règle commits), message décrivant budget + garde-fou tags.
- Concept : la chaîne d'échec : `make` s'arrête au premier code ≠ 0 ; un plan « réussi » Terraform peut être refusé par ta politique.
- Indice : `git ls-files infra | grep -E 'tfstate|tfplan|tfvars'` doit être vide avant le commit.
- Vérifier : `make plan; echo "exit=$?"` → `exit=0` ; avec la ressource « oops » → `exit≠0` ; `git log --oneline -1` montre le commit ; `git ls-files infra | grep -E 'tfstate|tfplan|tfvars'` vide.

## Pièges courants (Terraform / AWS, et le script Python)
1. **Budgets en USD seulement** : « 30 € » devient `limit_unit = "USD"` + un montant converti ; documenter le taux choisi dans un commentaire. Et la donnée coût a 8 à 24 h de retard : ne pas attendre l'alerte dans la minute.
2. **`default_tags` n'est pas une garantie** : une ressource qui pose `tags = { project = "x" }` gagne, certaines ressources ne reçoivent rien, et un module tiers peut ignorer le provider. C'est pour ça que l'étape 5 audite `tags_all` dans le plan, pas le code.
3. **Abonnement SNS `PendingConfirmation`** : `apply` vert, budget en place, zéro mail. Toujours vérifier `list-subscriptions-by-topic` et publier un message de test.
4. **Topic policy sans `Condition`** : `budgets.amazonaws.com` est un principal partagé par tous les comptes AWS ; sans `aws:SourceAccount`, n'importe quel budget d'un autre compte peut publier sur ton topic.
5. **Python : `tags_all` absent vs `null`** : `values.get("tags_all")` renvoie `None` dans les deux cas ; pour distinguer « non taggable » de « taggable sans tag », tester `"tags_all" in values`. Et `json.load` (fichier/stdin) ≠ `json.loads` (chaîne), `sys.exit(1)` et non `return 1` au niveau module.
