# S1-05 · Étude du flux BODACC (2 h)
Liste : S1 — Repo, Terraform, ingestion BODACC · Échéance : 2026-11-01 · Étiquettes : vert · [Carte Trello](https://trello.com/c/wEVuJFlQ)

## Objectif
Comprendre le flux BODACC tel qu'il est vraiment (endpoints, filtres, pagination et ses plafonds, champs imbriqués, volumes, heure de mise à jour) et le consigner dans `docs/source-bodacc.md` avec 5 annonces réelles — Pourquoi ça compte dans le projet : le client Python (S1-06), la Lambda d'ingestion (S1-07) et le MERGE Iceberg (S2-05) reposent sur ces faits ; une hypothèse fausse ici (pagination par offset, SIREN avec espaces, heure du scheduler) se paie trois cartes plus loin.

## Prérequis
### L'API Explore v2.1 d'OpenDataSoft
Le BODACC est publié par la DILA sur une instance OpenDataSoft : `https://bodacc-datadila.opendatasoft.com`, dataset `annonces-commerciales`. Trois endpoints à connaître : `/api/explore/v2.1/catalog/datasets/<dataset>` (métadonnées et liste des champs), `/records` (page de résultats, `limit` ≤ 100, `offset` + `limit` ≤ 10 000, `total_count` dans la réponse) et `/exports/jsonl` (flux complet filtré, une ligne JSON par annonce, sans plafond). Les filtres s'écrivent en ODSQL dans `where` (≈ une clause `WHERE` SQL passée en query string) ; `select`, `group_by`, `order_by` existent aussi. Pas de clé requise en lecture.
Doc : https://help.opendatasoft.com/apis/ods-explore-v2/ · https://bodacc-datadila.opendatasoft.com/explore/dataset/annonces-commerciales/information/
Exercice 5 min : ouvrir la page « Information » du dataset dans le navigateur, puis l'onglet « API » : retrouver l'URL `/records` générée et la comparer à celle de la doc Explore v2.1. Qu'est-ce qui change entre un filtre posé dans l'interface (`refine`) et un `where` ?

### Le BODACC : registres, familles, types d'avis
Chaque annonce a un `id` préfixé par son bulletin : `A` (ventes, créations, immatriculations), `B` (modifications, radiations, procédures collectives), `C` (dépôts des comptes). `familleavis` dit ce qui est annoncé (`creation`, `immatriculation`, `modification`, `radiation`, `collective`, `conciliation`, `vente`, `dpc`), `familleavis_lib` est le libellé humain. `typeavis` dit la nature de la publication : `annonce` (normal), `rectificatif` ou `annulation` d'une annonce précédente (`parutionavisprecedent`). Une entreprise est identifiée par son SIREN dans `registre` (liste de deux formes : `"130219660"` et `"130 219 660"`) et dans `listepersonnes`.
Doc : https://www.bodacc.fr/pages/a-propos/ · https://www.data.gouv.fr/datasets/bodacc-bulletin-officiel-des-annonces-civiles-et-commerciales/
Exercice 5 min : sur le site bodacc.fr, ouvrir une annonce de procédure collective et une radiation (lien `url_complete` d'un enregistrement). Noter quels champs de l'API correspondent à ce que tu vois à l'écran, et lesquels sont absents (le PDF, par exemple).

### JSON imbriqué en Python
`json.loads(texte)` ≈ `JSON.parse` : renvoie un `dict` (≈ objet), une `list` (≈ array), `str`, `int`, `None` (≈ `null`). Accès : `d["cle"]` lève `KeyError` si absent, `d.get("cle")` renvoie `None` (≈ `obj.cle ?? undefined`). Particularité BODACC : plusieurs champs (`listepersonnes`, `jugement`, `depot`, `radiationaurcs`, `registre`…) sont du **JSON sérialisé dans une chaîne** à l'intérieur du JSON : il faut un second `json.loads` sur la valeur. Le script d'exploration tient dans `python3 -c "…"` ou un fichier de 10 lignes, lu depuis `stdin` (`sys.stdin`).
Doc : https://docs.python.org/3/library/json.html · https://docs.python.org/3/tutorial/datastructures.html#dictionaries
Exercice 5 min : `python3 -c 'import json; s = "{\"a\": \"{\\\"b\\\": 1}\"}"; d = json.loads(s); print(type(d["a"]), json.loads(d["a"])["b"])` → `<class 'str'> 1`. Expliquer en une phrase pourquoi le premier `loads` ne suffit pas.

### Explorer une API depuis le terminal
`curl -s --compressed "<url>" | python3 -c "…"` est l'outil d'exploration de la carte : `-s` silencieux, `--compressed` indispensable ici (le serveur renvoie du gzip ; sans l'option, Python reçoit des octets `0x8b` illisibles), `-D -` pour voir les en-têtes (`X-RateLimit-*`), `-w "%{http_code}"` pour le code HTTP. Les caractères spéciaux de `where` (`=`, `'`, `"`, espace) doivent être encodés (`%3D`, `%27`, `%22`, `%20`) ou passés via `--data-urlencode` avec `-G`.
Doc : https://curl.se/docs/manpage.html · https://docs.python.org/3/library/sys.html#sys.stdin
Exercice 5 min : `curl -s -G --compressed "https://bodacc-datadila.opendatasoft.com/api/explore/v2.1/catalog/datasets/annonces-commerciales/records" --data-urlencode "where=familleavis='radiation'" --data-urlencode "limit=1"` → une annonce. Refaire sans `--compressed` : observer la sortie.

- Question : `json.tool` ? → module stdlib qui indente du JSON lu sur stdin, utile seulement pour regarder une réponse brute.

- Indice : `python3 -c "import json, sys; d = json.load(sys.stdin); …"` lit la réponse de `curl` sur stdin. `data_processed` est en UTC : convertir en heure de Paris avant de conclure sur le scheduler (06:17 UTC ≠ 06:17 Paris).
- Vérifier : `curl -s --compressed "$BODACC" | python3 -c "import json,sys; d=json.load(sys.stdin); print(len(d['fields']), d['metas']['default']['records_count'], d['metas']['default']['data_processed'])"` → `32 5xxxxxxx 2026-10-2xT06:1x…` (≈ 51 millions, mise à jour le matin UTC)

- Résultat : 11 champs `text` candidats JSON-dans-JSON pour l'étape 4 : `registre`, `listepersonnes`, `listeetablissements`, `jugement`, `acte`, `modificationsgenerales`, `radiationaurcs`, `depot`, `listeprecedentexploitant`, `listeprecedentproprietaire`, `parutionavisprecedent`. ### [x] Étape 2 — Filtrer une journée en ODSQL et mesurer les volumes
- À faire :
  1. `curl -s -G --compressed "$BODACC/records" --data-urlencode "where=dateparution=date'2026-10-20'" --data-urlencode "limit=1" | python3 -c "import json,sys; print(json.load(sys.stdin)['total_count'])"` : total de la journée. `limit=1` suffit, le serveur compte tout et ne renvoie qu'une ligne.
  2. `curl -s -G --compressed "$BODACC/records" --data-urlencode "where=dateparution=date'2026-10-20'" --data-urlencode "select=familleavis,count(*) as n" --data-urlencode "group_by=familleavis" | python3 -c "import json,sys; [print(r['familleavis'], r['n']) for r in json.load(sys.stdin)['results']]"` : volumes par famille.
  3. Même commande avec `typeavis` à la place de `familleavis` dans `select`, `group_by` et le `print`.
  4. `curl -s -G --compressed "$BODACC/records" --data-urlencode "where=dateparution='2026-10-20'" --data-urlencode "limit=1" | python3 -m json.tool` : provoquer l'erreur de type, exprès, pour la reconnaître plus tard.
- Concept : c'est quoi : ODSQL est le mini-SQL d'OpenDataSoft passé en query string (`where`, `select`, `group_by`, `order_by`). Pourquoi ici : la Lambda d'ingestion récupère « une journée » ; il faut savoir ce que ça pèse (≈ 32 000 annonces, dont ≈ 15 000 dépôts de comptes) et quelles familles le pipeline doit garder (création, collective, radiation) ou ignorer. Objectif : un tableau famille → volume pour une journée réelle.
- Cours : BODACC = Bulletin Officiel Des Annonces Civiles et Commerciales. Journal officiel de la vie des entreprises (créations, modifications, procédures collectives, radiations, dépôts de comptes, ventes), publié par la DILA, alimenté par les greffes. Publication légale obligatoire, donc exhaustif et horodaté, avec SIREN.
- Cours : OpenDataSoft = éditeur SaaS d'open data (≈ Supabase/Hasura pour datasets publics) ; la DILA y héberge le BODACC, comme SNCF ou Paris y hébergent les leurs. Deux noms : Explore API v2.1 = l'API REST ; ODSQL = le langage de requête passé dans `where`/`select`/`group_by`. `BodaccClient` (S1-06) est en fait un client ODS spécialisé.
- Cours : une ligne `--data-urlencode "where=dateparution=date'2026-10-20'"` empile trois couches : option curl (shell) → paramètre de query string `where` (HTTP) → expression ODSQL `dateparution=date'2026-10-20'` (serveur). `date'…'` = littéral typé, comme `DATE '2026-10-20'` en Postgres. Équivalent TS : `url.searchParams.set("where", "dateparution=date'2026-10-20'")`.
- Cours : ODSQL = sous-ensemble SQL, un dataset à la fois. Pas de `JOIN`, sous-requête, `UNION`. Dispo : `where` (`=`, `>`, `and`, `or`, `in`, `like`, `is null`, fonctions date), `select` avec agrégats, `group_by`, `order_by`, `limit`, `offset`. Les champs imbriqués sont du texte pour lui : pas de filtre sur `typePersonne`. Jointure BODACC × SIRENE → PySpark/Athena (S2). ODSQL sert à réduire ce qu'on télécharge, le SQL se fait dans le lakehouse.
- Question : OpenDataSoft, c'est un langage ? → non, un éditeur de plateforme ; le langage est ODSQL.
- Question : on peut faire n'importe quelle requête SQL, même des jointures ? → non, mono-dataset, filtre/agrégat seulement ; les jointures se font côté lakehouse.
- Erreur vue : `IncompatibleTypesInComparisonFilter — Left type: date, right_type: text` → `where=dateparution='2026-10-20'` compare une colonne `date` à une chaîne ; il faut `date'2026-10-20'`. Réponse HTTP 400, JSON `{error_code, message}` : en S1-06, lever une exception sur `error_code`, pas sur le texte.
- Indice : encoder le `where` (`dateparution%3Ddate'2026-10-20'`) ou utiliser `curl -G --data-urlencode "where=dateparution=date'2026-10-20'"`. Si tu obtiens `IncompatibleTypesInComparisonFilter`, c'est le littéral date qui manque. La famille « procédures collectives » s'appelle `collective`, pas `procedurecollective`.
- Vérifier : `curl -s -G --compressed "$BODACC/records" --data-urlencode "where=dateparution=date'2026-10-20'" --data-urlencode "select=familleavis,count(*) as n" --data-urlencode "group_by=familleavis" | python3 -c "import json,sys; [print(r['familleavis'], r['n']) for r in json.load(sys.stdin)['results']]"` → 8 lignes dont `creation 6813`, `collective 937`, `radiation 3104`, `dpc 15310` ; `curl -s -G --compressed "$BODACC/records" --data-urlencode "where=dateparution=date'2026-10-20'" --data-urlencode "limit=1" | python3 -c "import json,sys; print(json.load(sys.stdin)['total_count'])"` → `32373`
- Résultat : total 2026-10-20 = 32 373. Familles : `dpc` 15310, `creation` 6813, `modification` 5363, `radiation` 3104, `collective` 937, `immatriculation` 475, `vente` 370, `conciliation` 1. Cibles (`creation` + `collective` + `radiation`) = 10 854, un tiers ; `dpc` seul = 47 %. Filtrer à la source avec `familleavis in (...)` divise par 3 le téléchargement.
- Résultat : `typeavis` : `annonce` 32182, `annulation` 166, `rectificatif` 25. 0,6 % mais pas nul : à traiter en S2-05. `conciliation 1` : famille rare, existe → `familleavis` en `Literal[...]` à 8 valeurs dans Pydantic, pas `str` libre.

### [x] Étape 3 — Pagination : plafonds de `/records`, export JSONL, keyset
- À faire :
  1. `curl -s --compressed -o /dev/null -w "%{http_code}\n" "$BODACC/records?limit=101"` → `400` ; même commande avec `limit=1&offset=10000` → `400` ; avec `offset=9999` → `200`. Frontière exacte : `offset + limit ≤ 10 000`.
  2. `time curl -s -G --compressed "$BODACC/exports/jsonl" --data-urlencode "where=dateparution=date'2026-10-20'" --data-urlencode "select=id" | wc -l` : export des ids seuls, compter et chronométrer.
  3. `time curl -s -G --compressed "$BODACC/exports/jsonl" --data-urlencode "where=dateparution=date'2026-10-20'" -o day.jsonl` puis `wc -lc day.jsonl` : export complet, poids et durée. Garder le fichier pour l'étape 4.
  4. `curl -s -G --compressed "$BODACC/records" --data-urlencode "where=dateparution=date'2026-10-20'" --data-urlencode "order_by=id" --data-urlencode "limit=100" --data-urlencode "select=id" | python3 -c "import json,sys; r=json.load(sys.stdin)['results']; print(r[0]['id'], '...', r[-1]['id'])"` : première page triée par `id`.
  5. Tenter la page suivante avec `and id > 'A20260201100'` : erreur. Lire la réponse brute avec `python3 -m json.tool` avant de parser.
  6. Keyset qui marche : `--data-urlencode "where=dateparution=date'2026-10-20' and publicationavis='A' and numeroannonce > 100" --data-urlencode "order_by=numeroannonce"`, une boucle par bulletin A, B, C.
  7. Écrire la décision pour `fetch_day` avec les chiffres.
- Concept : c'est quoi : la pagination par offset demande au serveur de « sauter » N lignes, coûteux, donc plafonné ; le keyset pagine par « ce qui vient après la dernière clé » ; l'export est un flux complet en streaming. Pourquoi ici : `BodaccClient.fetch_day(date) -> Iterator[dict]` (S1-06) doit pouvoir itérer 32 000 annonces sans tenir tout en mémoire ni dépasser 10 000. Objectif : stratégie choisie, chiffres à l'appui (nombre d'appels, durée, mémoire).
- Cours : trois façons de lire 32 373 lignes. Offset = « saute N, donne 100 », le serveur retrie à chaque appel, coût croissant, donc plafonné. Keyset = « donne les 100 suivantes après la dernière clé vue », coût constant, exige une clé ordonnable et unique. Export = une requête, flux complet, une ligne JSON par annonce, pas de plafond, mais une seule connexion longue. Même question qu'en Next devant une grosse liste REST : page par page ou tout d'un coup.
- Cours : en ODSQL, `'…'` (simples) = littéral chaîne, `"…"` (doubles) = nom de champ, comme en SQL standard. `id > "A20260201100"` compare `id` à une colonne inexistante.
- Cours : `-o /dev/null -w "%{http_code}\n"` jette le corps et imprime le code HTTP. `time` en zsh : lire `total`. `wc -lc` = lignes + octets ; octets ÷ lignes = poids moyen d'une annonce.
- Cours : `id` = `A` + parution `20260201` + `numeroannonce` sans zéro de tête → longueur variable (`A202602011` … `A20260201100`), ordre lexical ≠ ordre numérique. Par bulletin (`publicationavis` A, B, C), `numeroannonce` est contigu de 1 à n ; le même numéro existe dans A, B et C, donc la clé keyset est le couple `(publicationavis, numeroannonce)`.
- Cours : `count(distinct …)` d'ODS est approximatif (HyperLogLog) : 8751 pour 8596 lignes. Ne jamais s'en servir pour un contrôle de complétude ; `total_count` est exact.
- Question : on ne comprend rien à cette étape ni au livrable ? → la question est « comment télécharger les 32 000 annonces d'une journée ? » ; le livrable est une phrase de décision chiffrée pour `docs/source-bodacc.md`, qui dira à S1-06 comment coder `fetch_day`.
- Erreur vue : `KeyError: 'results'` → la réponse n'a pas de clé `results`, donc c'est une erreur serveur en JSON ; réflexe : regarder la réponse brute avant de parser.
- Erreur vue : `IncompatibleTypesInComparisonFilter — Left type: text, right_type: text` sur `id > 'A20260201100'` → ODSQL n'autorise `>` que sur `int` et `date`, jamais sur `text`. Keyset sur `id` impossible ; le plan initial se trompait.
- Indice : l'export est une seule requête HTTP mais longue : penser timeout et lecture en streaming (`httpx` `stream()` + `iter_lines()`, S1-06). Le keyset fait ≈ 325 appels de 100 pour une journée (A 86 + B 85 + C 154) et dépend de la contiguïté de `numeroannonce`. `curl -o /dev/null -w "%{http_code}"` pour ne voir que le code HTTP.
- Vérifier : `curl -s --compressed -o /dev/null -w "%{http_code}\n" "$BODACC/records?limit=101"` → `400` ; `curl -s --compressed -o /dev/null -w "%{http_code}\n" "$BODACC/records?limit=1&offset=10000"` → `400` ; `curl -s -G --compressed "$BODACC/exports/jsonl" --data-urlencode "where=dateparution=date'2026-10-20'" --data-urlencode "select=id" | wc -l` → `32373` en quelques secondes
- Résultat : plafonds confirmés : `limit=101` → 400, `offset=10000` → 400, `offset=9999` → 200. Export ids : 32 373 lignes en 4,0 s. Export complet : 32 373 lignes, 59 432 342 octets (59 Mo, ≈ 1 835 octets par annonce) en 5,1 s. Le temps est côté serveur, pas transfert.
- Résultat : keyset sur `id` impossible (`text`). Keyset possible sur `(publicationavis, numeroannonce)` : `numeroannonce > 100` + `order_by=numeroannonce` → 200, 32 073 restants ; A 1→8596, B 1→8467, C 1→15310, contigus. Coût : 325 appels, 3 boucles.
- Résultat : décision pour `fetch_day` : **export JSONL**, 1 appel au lieu de 325, 5 s, code simple. Conditions côté client (S1-06) : timeout ≥ 60 s, lecture en streaming ligne par ligne (`iter_lines`), jamais 59 Mo en mémoire. Keyset `(publicationavis, numeroannonce)` documenté comme plan B si l'export devient instable. Décision prise sur recommandation du tuteur.

## Pièges courants (dev TS → Python)
1. `where=dateparution="2026-10-20"` échoue (`IncompatibleTypesInComparisonFilter`) : un champ `date` se compare à un littéral `date'2026-10-20'`.
2. `curl` sans `--compressed` : réponse gzip brute, `json.load` plante sur `0x8b`. Côté `httpx`, la décompression est automatique.
3. `offset + limit ≤ 10 000` et `limit ≤ 100` : une journée (≈ 32 k) ne se pagine pas par offset. Export JSONL en streaming ; keyset possible seulement sur un champ `int` ou `date` (`numeroannonce` par bulletin), jamais sur `id` qui est `text`.
4. `listepersonnes`, `jugement`, `depot`, `radiationaurcs` sont des chaînes JSON : `json.loads` deux fois. `personne` est tantôt un dict, tantôt une liste ; `prenom` aussi.
5. `registre` contient le SIREN deux fois (avec et sans espaces) ; `numeroIdentification` a des espaces. Normaliser en 9 chiffres avant toute jointure.
6. Famille « procédures collectives » = `collective` ; les dépôts de comptes (`dpc`) représentent près de la moitié du volume et ne servent pas au projet.
7. `typeavis` `annulation` / `rectificatif` référencent une annonce antérieure (`parutionavisprecedent`) : ignorer ces lignes ou les traiter mal crée des doublons ou des fantômes dans `events`.
8. `data_processed` est en UTC : 06:17 UTC = 08:17 à Paris en octobre. Un scheduler à 06:30 Paris lirait une journée incomplète.
9. En Python, `d["cle"]` lève `KeyError` si la clé manque (pas `undefined`) : `d.get("cle")` pour les champs optionnels.
10. Le SIREN n'est pas toujours dans `numeroImmatriculation` : artisans → `inscriptionRM.numeroIdentificationRM` ; `nonInscrit` → aucun SIREN.
